# Архитектура

## Административная панель

`app/admin` содержит `/orders`, `/products`, `/products/[productId]`, `/agents`
и `/agents/[agentId]`; `/admin` перенаправляет на заказы. Последний маршрут
собирает три widget через slots, без cross-widget imports. Бот имеет вкладки
заказов, товаров и настроек. Детали заказа открываются в Drawer, отдельного
order route нет. Фильтры и страницы хранятся в URL, редактор принимает
проверенный локальный `returnTo`.

Widgets `admin-shell`, `admin-orders`, `admin-products`, `admin-agents`,
`admin-agent-details` собирают features `admin-access`, `admin-product-management`,
`admin-order-action`, `admin-agent-settings`. Доменные DTO/API/queries находятся
в соответствующих entities, включая новую `agent`. Обычные seller forms и
mutations не используются для административной записи.

`AdminAccess` после `RequireAuth` проверяет свежий session-scoped профиль.
Дочерние widgets монтируются только для ADMIN. Правила кэша и API описаны в
[api-and-auth.md](./api-and-auth.md#административный-api).

`AppLayout` имеет отдельную ветку `/admin` без витринных header/footer/bottom
navigation, с общим NotificationProvider. Providers и тема остаются общими.
Desktop от 900 px использует sidebar и таблицы, mobile — Drawer меню и карточки;
панель заказа на мобильном полноэкранная. Административная навигация между
страницами — нативные ссылки: уход из изменённых форм защищает beforeunload;
данные форм не сохраняются в браузерное хранилище. Изменение query фильтров
списка использует router.replace без перезагрузки.

Метрика подключается только в витринной ветке. При клиентском пересечении
границы витрина/admin контент новой ветки не монтируется до полной навигации,
чтобы Webvisor не наблюдал административные данные. `/admin` имеет noindex,
запрет в robots и не входит в явный перечень sitemap.

Figurzilla — frontend marketplace на Next.js App Router. Backend находится в отдельном проекте, поэтому новые endpoint'ы, поля и статусы добавляются только по подтверждённому контракту.

## Структура

```txt
app/          Next.js routes, layouts, metadata, errors, route handlers
src/app/      providers, theme, app-level config и analytics
src/widgets/  крупные блоки страниц
src/features/ пользовательские сценарии и действия
src/entities/ доменные модели, API и entity UI
src/shared/   общая инфраструктура, utilities и нейтральный UI
tests/        smoke и e2e
docs/         документация
```

Корневой `app/` отвечает за маршрутизацию. Route-файлы должны оставаться тонкими: получать параметры, настраивать metadata и собирать нижние слои.

Product detail, seller edit и admin product/agent routes проверяют положительный
safe integer до загрузки. Category route проверяет ID каждого slug. Неверный
синтаксис вызывает `notFound()` вне catch; временная ошибка загрузки остаётся
ошибкой с retry. Для admin pagination неверный page нормализуется в 0,
невалидный agent filter исключается. SSR not-found добавляет `noindex`;
после начала streaming ответ может иметь HTTP 200 вместо 404.

Асинхронные route-сегменты с серверной загрузкой данных используют локальный
`loading.tsx`, который делегирует отображение skeleton соответствующему widget.
Главная страница изолирована в route group `app/(home)/`, чтобы её fallback не
применялся к остальным маршрутам; публичный URL остаётся `/`.

## FSD-границы

```txt
app -> widgets -> features -> entities -> shared
```

- **`shared`**
  - Ответственность: HTTP clients, config, общие hooks, нейтральные types и UI.
  - Зависимости: только внешние пакеты.
- **`entities`**
  - Ответственность: доменные API, query keys, модели и небольшой UI.
  - Зависимости: `shared`.
- **`features`**
  - Ответственность: действия, формы и сценарии.
  - Зависимости: `entities`, `shared`.
- **`widgets`**
  - Ответственность: композиция экранных блоков.
  - Зависимости: `features`, `entities`, `shared`.
- **`app`**
  - Ответственность: routes, providers и app config.
  - Зависимости: все нижние слои.

Правила:

- не импортировать верхний слой в нижний;
- между слайсами использовать `index.ts`, если public API существует;
- не делать cross-feature imports без существующего обоснованного паттерна;
- внутри слайса допустимы короткие относительные imports;
- `@x` использовать только для узкого межслайсового контракта entities.

Проверка границ настроена в `steiger.config.mjs`. `npm run architecture:check`
запускает Steiger для `src`; все recommended rules обязательны, кроме
`fsd/insignificant-slice`. Эта эвристика отключена, потому что фактический
app layer находится в корневом `app/`, вне `src`.

Корневой `app/` не входит в автоматическую область Steiger. Направление его
импортов, тонкость route-файлов и композиция нижних слоёв проверяются вручную
при review.

## Размещение кода

- route, layout, metadata, error page — `app/`;
- provider, theme, analytics — `src/app/`;
- крупный блок страницы — `src/widgets/<slice>`;
- пользовательское действие — `src/features/<slice>`;
- доменная модель, API, query hooks — `src/entities/<slice>`;
- общая утилита или нейтральный UI — `src/shared`.

Доменные DTO размещаются в `model` соответствующих entities. `entities/image`
владеет image DTO, API, query hooks и связыванием изображений с доменными
данными. Core DTO профиля, заказов и собственных товаров кэшируются отдельно;
widgets собирают визуальные модели через `mapImageMetadata` и существующий
image query с локальными loading/error/fallback/retry. Контракты и ключи
описаны в [api-and-auth.md](./api-and-auth.md#поиск-товаров-и-сессия).
`entities/session` владеет auth API, Zustand store, auth hooks,
инициализацией и refresh lifecycle. В `src/shared/model`, доступном через
`@/shared/types`, остаётся только нейтральный тип `Currency`.

Axios clients остаются в `shared`. Они не импортируют session store:
`AuthProvider` регистрирует `AuthSessionAdapter`, через который interceptor
запрашивает refresh и сообщает об истечении сессии.
Adapter также передаёт сигнал поколения сессии для отмены устаревших ожиданий
и replay. Общим pending refresh и записью токенов владеет session store;
детали lifecycle описаны в [api-and-auth.md](./api-and-auth.md#текущий-auth-flow).

Авторизация публичного поиска передаётся из композиции: `useAuth.sessionKey`
поступает в опции `useProductsInfinite`. Entity товара не импортирует session;
правила изоляции query cache и гостевого SSR описаны в
[api-and-auth.md](./api-and-auth.md#поиск-товаров-и-сессия).

Server state хранится в TanStack Query. Zustand используется для клиентского состояния.

`PrivateDataBoundary` в app providers задаёт владельца приватных данных через
`PrivateScopeContext` из `shared/lib/query`. Entities используют `scope.key`
и `usePrivateMutation`, не импортируя session из соседнего слайса. Граница
также вызывает public API `clearProductFormDraft` widget создания товара.
Правила ключей, teardown и восстановления черновика описаны в
[api-and-auth.md](./api-and-auth.md#server-и-client-state).

Подтверждённое исключение — `cartQuantityStore`: он хранит optimistic projection количества, revisions, sync status и последнее подтверждённое значение, синхронизируясь с cart query. Источником истины об актуальной корзине и остатках остаётся backend/TanStack Query; Zustand не должен превращаться во второй независимый cache.

## Импорты

Алиасы из `tsconfig.json`:

```json
{
  "@/shared/hooks": ["./src/shared/lib/hooks"],
  "@/shared/types": ["./src/shared/model"],
  "@/*": ["./src/*"]
}
```

Для кода из `src/` предпочтителен `@/...`. Новые aliases не добавляются без отдельного решения.

## UI и формы

`ProductPriceDisplay` требует `currency` из товара; карточки каталога и собственных
товаров передают её явно. Цены, предоплата и остаток в карточках и деталях используют
общий `formatPrice`, как корзина и оплата: исходная валюта, до двух дробных знаков,
без конвертации и изменения расчётов.

- использовать Material UI и тему из `src/app/config/theme.ts`;
- сначала проверять готовые компоненты в `src/shared/ui`;
- не размещать API-вызовы и бизнес-логику в `shared/ui`;
- для нетривиальных форм использовать React Hook Form;
- API-зависимый UI должен обрабатывать loading, error, empty и success;
- skeleton должен повторять геометрию и responsive-layout своего success-state;
- неизвестные до ответа условные секции не резервируются как обязательные;
- доменные и экранные skeletons размещаются рядом с entity/widget, а нейтральные
  компоненты из `shared` получают loading UI через слот;
- payload и validation rules не менять без подтверждённого backend-контракта.

Цветовые роли общие для всех viewport: `primary.main` и `secondary.main`
сохраняют фирменные розовый и голубой; `primary.dark` используется для
розовых заливок с белым текстом, `palette.accent` — для контрастного текста
на светлых подложках. `preorder` задаёт голубые кнопки и бейджи предзаказа;
цвет избранного — розовый, error/success обозначают служебные состояния.
Warning использует янтарные заливки и светлые подложки с тёмным
`warning.contrastText`; `warning.main` и `warning.dark` не используются для
мелкого текста на белом фоне. Это правило относится также к статусам заказов,
остаткам товаров, продлению и уведомлениям.
Сброс стилей ссылок находится в `MuiCssBaseline`, внутри CSS-слоя MUI,
чтобы не перекрывать цвета кнопок-ссылок и выбранной навигации.
Фокус использует непрозрачную обводку; шапка задаёт тёмный цвет через
`--focus-ring-color` для контраста на голубой поверхности.

## Responsive rendering

Тема задаёт единый набор breakpoints: `xs=0`, `sm=600`, `md=900`,
`lg=1376`, `xl=1536`. Для описания режимов используются границы compact
`<600`, medium `600–899` и wide `>=900`; двухколоночная карточка товара
включается с `lg=1376`.

SSR-visible UI строится CSS-first: сервер и первый клиентский render должны
иметь одно DOM-дерево, а размеры, порядок и видимость представительных
элементов задаются responsive `sx`, Grid/Flex и media queries в CSS.
`useMediaQuery`, UA detection и серверное угадывание viewport не используются
для выбора JSX-ветки, текста, количества детей или загружаемого asset.

`window.matchMedia` допустим только после mount для поведения без изменения
первоначального DOM, например для scroll listener, либо в момент открытия
разных overlay surfaces. Responsive изображения с разными файлами оформляются
через art direction (`picture`/`source`), чтобы браузер не загружал оба варианта.

### Route-aware application shell

Для витрины `AppLayout` получает pathname и состояние гостевой сессии и через чистый resolver выбирает mobile chrome:
`browse`, `context`, `account`, `focused` или `auth`. Конфигурация определяет
родительский заголовок и fallback для Back, наличие нижней навигации, mobile
footer и меню кабинета; маршрутизация App Router при этом не дублируется и не
перестраивается.

На ширине `<900` верхняя панель занимает `56 px` в compact и `64 px` в medium
плюс `safe-area-inset-top`. На wide сохраняется desktop header `119 px`.
Нижняя навигация высотой `64 px` плюс `safe-area-inset-bottom` содержит
«Главная», «Категории», «Корзина», «Избранное» и «Профиль» и показывается только
на разрешённых resolver'ом маршрутах. Browse-экраны и продавец сохраняют
нижнюю навигацию; product detail, авторизованный checkout, auth и редактор товара используют
focused/context chrome без неё. Dashboard использует account chrome, а
информационные страницы — context chrome с footer.

После инициализации сессии гостевой `/checkout` использует browse chrome с
поиском и нижней навигацией, без mobile footer. Гостевой `/favorites` сохраняет
browse chrome; `Footer` получает `mobileCompact`, который до `900 px` оставляет
контакты, юридические ссылки и копирайт вместо полной навигации. Desktop footer
сохраняет прежнюю композицию. Гостевые состояния обеих страниц имеют заголовок
раздела и уточнённые тексты на всех размерах; тематические иконки, вертикальные
кнопки `48 px` и отдельный переход в каталог применяются только до `900 px`.

На мобильном `/dashboard` widget `dashboard-home` показывает компактный профиль
и прямой список разделов; прогресс заполнения и плитки обзора скрыты до `900 px`.
Список остаётся доступным при загрузке и ошибке данных профиля, но скрывается
во время редактирования. Skeleton повторяет компактный профиль, ошибка позволяет
повторить его загрузку. Корневой маршрут не открывает отдельное меню кабинета;
на вложенных account-маршрутах меню сохраняется. Desktop-композиция не меняется.

Для `/dashboard/purchase`, `/dashboard/sales`, `/dashboard/products/new`,
`/dashboard/settings` и `/dashboard/security`
resolver задаёт отдельный `title` текущего раздела: Header выводит его как `h1`
на мобильных, а `parentLabel` остаётся названием назначения Back. Повторный
PageHeader этих экранов скрыт до `900 px`; правила «Моих товаров» и edit-маршрута
сохраняются.

В `dashboard-settings` до `900 px` четыре короткие вкладки видны одновременно;
посещённые панели остаются смонтированы и сохраняют ввод при переключении и resize.
Маркеры вкладок показывают несохранённые изменения. Начальное раскрытие карточек
на desktop восстанавливается после mount; на мобильных карточки начинаются
свёрнутыми, открытие одной закрывает остальные без сброса полей.
Ошибки справочников и пользовательских настроек имеют retry и блокируют запись;
загруженная форма остаётся смонтирована при ошибке фонового запроса.

Локальный `useSettingsDraft` хранит базу сравнения React Hook Form отдельно от
изменяющегося Query cache. Фоновая загрузка не заменяет dirty-ввод. Мутации
выполняются последовательно; после них выполняется чтение подтверждённых данных.
При частичном успехе введённые значения сохраняются, повтор отправляет только
отличия от подтверждённой базы. Если итоговое чтение не удалось, новые записи
блокируются до retry чтения: create-контракты не возвращают ID. Выключение
существующего способа обозначается как удаление после сохранения. Черновики
реквизитов и пароли не сохраняются в browser storage.

Панель сохранения активной вкладки появляется на мобильных при изменениях,
учитывает shell offsets и Visual Viewport, резервирует место под собой и передаёт
свой отступ уведомлениям. Адресная форма использует собственные действия;
компактное отображение адресов включается только настройками. `dashboard-security`
сохраняет существующий контракт смены пароля, поддерживает password autocomplete,
постоянную подсказку требований и ошибку запроса внутри формы. Успех очищает поля
и сбрасывает их видимость, ошибка сохраняет ввод.

В `widgets/orders` мобильная композиция содержит один список: сначала заказы,
требующие действия, затем остальные активные и завершённые. Фильтры и сортировка
локальны и используют загруженные заказы и доменные правила; отдельные запросы
для счётчиков не выполняются. На мобильных доступны быстрые фильтры и диалог
с применением выбора, компактные loading/error/empty states с retry и ссылками.
Desktop-композиция переключается CSS; общий диалог деталей сохраняется при resize
и занимает весь экран ниже `900 px`. Некорректный комментарий истории пропускается.

Начальная ошибка заказов показывает error/retry; ошибка фонового чтения сохраняет
список и открытые формы. Локальный context `widgets/orders` блокирует новые действия
до успешного retry, не прерывая pending-запись и её результат. Feature-диалоги оплаты
и подтверждения принимают `actionsAvailable`, `onRetry`, `retryPending`: загрузку можно
повторить внутри открытого диалога. Остальные order-диалоги читают context
внутри widget. Cancel/review используют только переданный open-state: все способы
закрытия защищены pending guard, reset выполняется при следующем открытии или после
выхода анимации того же открытия. Поздний callback не меняет новое открытие.
`useOrderCancelAction.cancelOrder` возвращает promise settlement и принимает callback
успеха конкретной операции. Ввод остаётся в локальном состоянии компонентов.

Admin-редактор сохраняет последнюю подтверждённую базу связей и смонтированную форму
при ошибке фонового чтения или mapping. Новые save/restore заблокированы до успешной
загрузки; dirty-поля не заменяются refetch. База привязана к session и ID товара.

Мобильный create-режим `widgets/create-product-form` использует компактную загрузку
фото, отдельный диалог поиска и множественного выбора категорий, а также закреплённую
панель публикации с переходами к незаполненным полям. Выбор категорий применяется
по «Готово». Состояние React Hook Form сохраняется при resize; edit-режим и desktop
сохраняют прежнюю компоновку. Очистка непустой мобильной формы требует подтверждения.
Статус локального черновика отличает успешное сохранение от хранения только в памяти
и ошибки удаления. Ошибка восстановления фото сохраняет их ID, блокирует публикацию
и позволяет повторить загрузку. Контракт формы и правила валидации не изменены.

Отправка create/edit принадлежит экземпляру формы: синхронная блокировка исключает
повторную запись, а поля, категории, фото и сброс недоступны до завершения операции
и перехода. Ошибка записи сохраняет ввод. Подтверждённый edit обновляет baseline
полей и imageIds до cleanup; смена режима/товара создаёт новый экземпляр формы.
Правила завершения и очистки черновика описаны в [api-and-auth.md](./api-and-auth.md).

Mobile search открывается отдельным fullscreen dialog без категорий. Пункт
«Категории» открывает другой fullscreen dialog, где поиск товаров расположен
над иерархией категорий. Overlay surfaces используют `100dvh`, safe areas,
focus trap и возврат фокуса; desktop search и categories drawer сохраняются.

Геометрия shell задаётся CSS-переменными `--shell-top-offset`,
`--shell-bottom-offset` и `--shell-sticky-top`. Контент, sticky/fixed controls,
уведомления и overlay gates должны использовать эти offsets вместо локальных
чисел. Закреплённая панель формы измеряет свою высоту и положение экранной клавиатуры
через Visual Viewport; её отступ `--shell-fixed-action-offset` на `html` поднимает
уведомления выше кнопки публикации и удаляется при размонтировании. Route-dependent bottom offset задаётся на корневом элементе через
`GlobalStyles`, чтобы его наследовали и MUI portals. Корневой viewport включает
`viewport-fit=cover`.

## Статус прежних отклонений

Ранее зафиксированные отклонения устранены:

- home, category и search варианты объединены в `widgets/product-catalog`;
  widget-to-widget dependencies удалены;
- доменные DTO и image-реализация перенесены в соответствующие entities;
- auth API, store и hooks перенесены в `entities/session`; `features/auth`
  содержит сценарный UI без проксирующих реэкспортов из `shared`;
- Axios отделён от session store через adapter, регистрируемый в app layer.

Автоматическая проверка не заменяет review public API, `@x`-контрактов и
корневого `app/`. Новые отклонения без архитектурного решения не добавляются.
