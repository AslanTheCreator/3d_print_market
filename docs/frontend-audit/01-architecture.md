# Аудит frontend: архитектура и FSD

Дата: 01.10.2026. Проект: Figurzilla, версия package.json — 1.27.0.
Проверенная ревизия: `8377939`; перед аудитом рабочее дерево было чистым.

## 1. Результат

Архитектура в целом позволяет развивать проект без переписывания. Направление
межслойных импортов соблюдено, зависимости между разными features и widgets не
найдены. Доменные API и модели преимущественно находятся в entities, общая
HTTP-инфраструктура отделена от session через adapter. Steiger проходит.

Обнаружены пять исправимых на frontend проблем:

| ID | Severity | Проблема | Effort |
| --- | --- | --- | --- |
| A1 | High | У жизненного цикла сессии нет единой границы очистки пользовательских данных | Medium |
| A2 | Medium | Entity-мутация смешивает сохранение товара и удаление файлов, теряя частичный успех | Medium |
| A3 | Medium | Shared-компонент владеет сценарием входа и расходится с остальными точками авторизации | Small |
| A4 | Low | Внутренние импорты через собственные public API создают два циклических компонента графа | Small |
| A5 | Low | Сохранились неиспользуемые альтернативные реализации товарных сценариев | Small |

Critical-проблем не найдено. High относится к изоляции клиентских данных между
сессиями, а не к формальным нарушениям расположения каталогов. Backend-проблемы,
неподтверждённые контракты и предложения изменить API в отчёт не включены.

## 2. Discovery и scope

### Изученные правила и конфигурация

- `AGENTS.md`, `docs/architecture.md`, релевантные разделы
  `docs/api-and-auth.md` и `docs/testing.md`.
- `package.json`, `tsconfig.json`, `steiger.config.mjs`, `.eslintrc.json`,
  `next.config.mjs`, `.github/workflows/frontend-ci.yml`.
- Дополнительных `AGENTS.md` внутри `app/` и `src/` не найдено; `.agents`
  не содержал дополнительных файлов с инструкциями.

Стек по package.json: Next.js 15, React 19, TypeScript со strict mode,
MUI/Emotion, TanStack Query 5, Zustand 5, React Hook Form 7, Axios, Playwright,
npm. Диапазоны package.json не трактовались как точные установленные версии.
Локальное окружение: Node.js 24.15.0, npm 11.12.1.

### Карта ответственности

| Область | Фактическая роль и связи |
| --- | --- |
| Корневой `app/` | Next.js routes, layouts, metadata, route handlers; собирает widgets/features/entities, использует отдельные server entry points |
| `src/app/` | Providers, тема, аналитика, shell; связывает session и HTTP adapter, располагает QueryClientProvider |
| `widgets` | Композиция каталога, деталей, кабинета, checkout и админки; 20 непустых слайсов |
| `features` | Действия с корзиной/избранным, auth, image upload, создание и этапы заказа, административные сценарии; 16 слайсов |
| `entities` | 15 доменных слайсов с DTO, API, queries, моделями и UI; межслайсовые связи через 17 `@x` entry points |
| `shared` | HTTP, env, токены, utilities, нейтральный UI; отдельные сценарные примеси рассмотрены в A3 |

Отдельного слоя `pages` нет. С учётом Next.js App Router и правил проекта это
не дефект: маршрутизация принадлежит корневому `app/`, экранные блоки — widgets.
Пустые старые каталоги widgets не считались действующими слайсами.

### Как выбран scope глубокого анализа

Сначала построен граф локальных импортов и реэкспортов для 551 файлов `.ts/.tsx`
в `app/` и `src/`: 49 в корневом `app/`, 12 в `src/app/`, 205 в widgets,
53 в features, 159 в entities и 73 в shared. Учтены относительные пути,
aliases из tsconfig, статические imports/exports и вызовы import/require со
строковым литералом. Проверены направление зависимостей, внешние deep imports
и сильно связные компоненты; type-only связи рассмотрены отдельно.

Затем подробно изучены связанные цепочки:

- routes → product-catalog/product-details → product/category → shared API;
- create-product-form → product/image-upload/user → product/image;
- checkout → order-create → cart/order/address/transfer;
- orders и admin-order-action → доменные правила заказа;
- session → AuthProvider/QueryProvider/AdminCacheBoundary → точки входа/выхода;
- public API и `@x`-контракты, а также shared UI, участвующий в этих сценариях.

Крупные модули проверялись по ответственности и связям, а не только по числу
строк. Весь репозиторий последовательно не перечитывался. Производительность
React, подробные настройки Query, правила форм, accessibility и визуальный UX
не были предметом этого этапа. Сессия и последствия ошибок мутаций рассмотрены
только там, где проблема обусловлена архитектурной границей ответственности.

## 3. Подтверждённые проблемы

### A1. Нет единой границы завершения и смены сессии

**Severity: High. Effort: Medium.**

**Файлы и конкретные места:**

- [authStore.ts](../../src/entities/session/model/authStore.ts#L71), `logout`,
  и ветка ошибки `refreshToken` ниже в этом модуле.
- [AuthProvider.tsx](../../src/app/providers/AuthProvider.tsx#L39), очистка
  только cart quantity state при переходе в guest.
- [AdminCacheBoundary.tsx](../../src/app/providers/AdminCacheBoundary.tsx#L8),
  централизованная очистка только ключей `admin`.
- [LogoutButton.tsx](../../src/features/auth/ui/LogoutButton.tsx#L24),
  очистка Query cache непосредственно в обработчике кнопки; аналогичная логика
  в `DashboardMobileNavigation.tsx` и `MobileAccountMenu.tsx`.
- [useUserQueries.ts](../../src/entities/user/model/useUserQueries.ts#L6),
  личные данные используют общие ключи `userKeys.current()` / `profile()`.
- [productFormDraft.ts](../../src/widgets/create-product-form/model/productFormDraft.ts#L11),
  один browser storage key и module-level memory draft без владельца.
- [useProductFormDraftState.ts](../../src/widgets/create-product-form/model/useProductFormDraftState.ts#L83),
  восстановление этого черновика без проверки аккаунта.

**Проблема.** `logout()` очищает токены и session store, но не задаёт полный
контракт завершения пользовательской сессии. Очистка остальных данных зависит
от вызывающего UI. Обычные кнопки удаляют query cache, а автоматические и прямые
переходы session state не обеспечивают ту же очистку. Provider сбрасывает
количества корзины; отдельная boundary корректно изолирует админку, но не
обычный кабинет. Черновик товара не очищается даже обычными кнопками выхода
и не разделяется по аккаунтам.

**Почему это проблема.** Инвариант «данные относятся к текущему аккаунту»
распределён между несвязанными модулями. Новый способ выхода или входа должен
знать обо всех потребителях session state. Очистка session не гарантирует
очистку персонального состояния приложения.

**Последствия.** После завершения сессии без полной перезагрузки и нового
входа может использоваться свежий по времени cache предыдущего пользователя.
Черновик с названием, описанием и ID изображений восстанавливается следующему
аккаунту в том же браузере даже после перезагрузки. Помимо раскрытия локальных
данных, это создаёт риск публикации чужого черновика; успешная публикация с
чужими image IDs не утверждается, поскольку зависит от backend-проверок.

**Подтверждение.** В изолированном Node-прогоне исполнены текущие `authStore`
и draft-модуль с подставным auth API и storage, использован настоящий
TanStack QueryClient и воспроизведена подписка AdminCacheBoundary.
Последовательность `logout → login` сохранила `['users', 'profile']` и черновик,
а старый `admin` cache был удалён. Это проверка модулей и архитектурного
инварианта; полный браузерный сценарий утечки не запускался. В HTTP-пути
`onSessionExpired` полная навигация действительно сбрасывает memory cache,
но не устраняет общий persisted draft и остальные пути завершения сессии.

**Исправление на frontend.** В app layer под QueryClientProvider ввести общую
session boundary, реагирующую на смену аккаунта/завершение сессии независимо
от кнопки или interceptor. Она должна отменять и удалять auth-bound queries,
сбрасывать пользовательские client stores и очищать memory draft. Для
persisted draft выбрать явную политику: удалять при выходе либо хранить под
проверенным идентификатором владельца и восстанавливать только ему. Общий
старый ключ не восстанавливать в другом аккаунте. Владельцы состояния должны
предоставлять небольшие cleanup API; session entity не должна импортировать
widgets или QueryProvider. Успешный refresh того же аккаунта не должен
уничтожать пользовательский ввод: использовать существующее различие
`accountRevision` и `sessionRevision`.

### A2. Entity-мутация скрывает частичный успех сценария редактирования

**Severity: Medium. Effort: Medium.**

**Файлы и конкретные места:**

- [useProductMutations.ts](../../src/entities/product/model/useProductMutations.ts#L18),
  `useUpdateProduct`, последовательность PUT товара → DELETE изображений,
  инвалидация только в `onSuccess`.
- [useProductForm.tsx](../../src/widgets/create-product-form/model/useProductForm.tsx#L238),
  вычисление `imageIdsToDelete` из сценарного состояния редактора.
- [productFormSubmit.ts](../../src/widgets/create-product-form/model/productFormSubmit.ts#L93),
  обработка результата как единого успеха либо ошибки.
- [imageApi.ts](../../src/entities/image/api/imageApi.ts#L91), `deleteImages`.

**Проблема.** Публичная мутация entity товара выполняет два отдельных действия
над разными сущностями. Успешный PUT уже сохраняет товар, но ошибка удаления
изображений отклоняет всю мутацию. Инвалидация товара не выполняется, UI получает
общую ошибку и не знает, что основная запись уже завершена.

**Почему это проблема.** Entity API включает политику конкретного редактора:
физическое удаление исключённых файлов. Неатомарный workflow представлен как
атомарная операция без состояния частичного успеха. Это мешает безопасно
переиспользовать обновление товара в других frontend-сценариях.

**Последствия.** Интерфейс и cache могут показывать старую запись после
успешного сохранения. Повторное нажатие сохранения повторяет PUT вместо
восстановления только незавершённого шага. Пользователь не может отличить
несохранённый товар от сохранённого товара с ошибкой очистки файлов.

**Подтверждение.** Текущие mutation options исполнены через настоящий
TanStack MutationCache с подставными API: PUT успешен, DELETE отклонён.
Получены status `error` и ноль вызовов invalidateQueries. Запросы к backend
и физическое удаление файлов не выполнялись.

**Исправление на frontend.** Оставить entity-мутации обновление товара и
инвалидацию сразу после подтверждённого PUT. Оркестрацию очистки файлов
поместить в сценарный model редактора — существующий widget или feature,
если сценарий потребуется в нескольких местах. Представлять этапы отдельно:
«товар сохранён» и «очистка не завершена». После ошибки второго шага не
повторять автоматически первый. Сохранить существующие endpoint/payload;
проверку необходимости физического удаления не заменять предположением
о backend. Сам по себе разрешённый импорт `image/@x/product` не является
нарушением FSD: дефект здесь в ответственности и обработке результата.

### A3. Сценарий входа встроен в shared и реализован непоследовательно

**Severity: Medium. Effort: Small.**

**Файлы и конкретные места:**

- [AuthRequiredDialog.tsx](../../src/shared/ui/auth-required-dialog/AuthRequiredDialog.tsx#L16),
  продуктовый `productName`, сценарный текст и `handleLogin` с прямым
  `router.push('/auth/login')`.
- [UnauthorizedState.tsx](../../src/shared/ui/states/UnauthorizedState.tsx#L74),
  самостоятельное построение auth URL с `redirect`.
- [RequireAuth.tsx](../../src/features/auth/ui/RequireAuth.tsx#L14),
  другая реализация того же перехода с `redirect`.
- `features/add-to-cart/ui/AddToCartButton.tsx` и
  `features/toggle-favorite/ui/FavoriteButton.tsx`: действующие потребители
  shared dialog.
- [authRedirect.ts](../../src/entities/session/model/authRedirect.ts#L3),
  существующие публичные правила возврата после входа.

**Проблема.** Shared dialog сам выбирает маршрут входа и содержит логику
сценария добавления товара. При этом его вариант перехода не передаёт
`redirect`, в отличие от guards и гостевых состояний. Нижний слой владеет
частью auth-политики приложения, а точки входа используют разные правила.

**Почему это проблема.** Место вызова не может задать продолжение сценария
через public props. Изменение auth-навигации требует искать бизнес-решения
в shared и features. Формально направленных вверх импортов нет, поэтому
Steiger эту проблему не обнаруживает.

**Последствия.** Гость, нажавший добавление в корзину или избранное на странице
товара, после входа получает `/`, поскольку bare `/auth/login` не содержит
адрес возврата. Это подтверждается кодом dialog и login page, где отсутствие
`redirect` нормализуется в `/`. Повторение самого действия после входа здесь
не требуется: речь о сохранении места сценария.

**Исправление на frontend.** Shared dialog должен принимать нейтральный
`onLogin`/href и содержимое, а маршрут и контекст возврата должны определять
вызывающие features или композиция widget. Использовать имеющиеся публичные
helpers `entities/session` для одинакового построения безопасного auth URL.
Аналогично постепенно вынести маршруты и доменные варианты UnauthorizedState
в его композицию. Не перемещать dialog в `features/auth` с последующим прямым
импортом из add-to-cart/toggle-favorite: это создаст cross-feature зависимость.
Новые endpoint и автоматический replay действия не нужны.

### A4. Собственные barrels создают циклы внутри entities

**Severity: Low. Effort: Small.**

**Файлы и конкретные места:**

- [cart/index.ts](../../src/entities/cart/index.ts#L29), реэкспорты hooks;
  [useCartChecks.ts](../../src/entities/cart/model/useCartChecks.ts#L1) и
  [useCartItemRemoval.ts](../../src/entities/cart/model/useCartItemRemoval.ts#L2)
  импортируют `@/entities/cart` внутри того же слайса.
- [favorite/index.ts](../../src/entities/favorite/index.ts#L8) и
  [useFavoritesChecks.ts](../../src/entities/favorite/model/useFavoritesChecks.ts#L1)
  образуют такую же связь.

**Проблема.** Найдены два сильно связных компонента value-import графа:

```text
cart/index → useCartChecks → cart/index
cart/index → useCartItemRemoval → cart/index
cart/index → useCartQuantity → useCartChecks → cart/index

favorite/index → useFavoritesChecks → favorite/index
```

Три пути корзины принадлежат одному циклическому компоненту, поэтому это
не четыре отдельных замечания. Результат совпал для графа со всеми imports
и графа без явно type-only imports.

**Почему это проблема.** Public API предназначен для потребителей слайса,
а его внутренние модули теперь зависят от полного набора реэкспортов. Изменения
barrel могут затрагивать внутренний порядок инициализации и расширять связи
между независимыми hooks.

**Последствия.** Усложняются изолированное тестирование и дальнейшее изменение
слайса; добавление top-level чтения импортируемого значения может сделать
цикл причиной ошибки инициализации. Текущий runtime crash не выявлен и не
утверждается: имеющиеся функции обращаются к зависимостям позднее, поэтому
Severity — Low.

**Исправление на frontend.** Внутри слайса заменить собственный barrel на
относительные imports нужных соседних модулей: queries, mutations, store.
Внешние imports через public API сохранить. После этого повторить проверку
графа циклов; одного Steiger недостаточно — текущую конфигурацию он пропускает.

### A5. Неиспользуемые товарные реализации создают альтернативные правила

**Severity: Low. Effort: Small.**

**Файлы и конкретные места:**

- [useCreateProductForm.tsx](../../src/widgets/create-product-form/model/useCreateProductForm.tsx#L20)
  и [model/index.ts](../../src/widgets/create-product-form/model/index.ts#L1).
- [CreateProductForm.tsx](../../src/widgets/create-product-form/ui/CreateProductForm.tsx#L20)
  использует другой hook, `useProductForm`.
- [ProductFormFields.tsx](../../src/entities/product/ui/ProductFormFields.tsx#L43)
  и [product/index.ts](../../src/entities/product/index.ts#L7).
- [ExternalPurchaseButton.tsx](../../src/features/external-purchase/ui/ExternalPurchaseButton.tsx#L29)
  и `features/external-purchase/index.ts`.

**Проблема.** Сохранены самостоятельный старый hook создания товара,
неиспользуемая сборка его полей в entity и неиспользуемая feature покупки
через Telegram. Поиск обращений в исходниках, тестах и остальных текстовых
файлах проекта, исключая документацию и generated artifacts, обнаружил только
определения и реэкспорты этих символов.

Старый hook содержит собственные readiness/submit правила без текущей проверки
настроек продавца и управления черновиком. ProductFormFields существует рядом
с действующими компонентами полей widget. ExternalPurchaseButton описывает
внешнюю покупку, хотя действующая композиция каталога использует AddToCartButton
и для `EXTERNAL_PRODUCT`.

**Почему это проблема.** При доработке товарных сценариев видны несколько
правдоподобных точек расширения, часть которых уже не соответствует рабочему
пути. Это подтверждённое расхождение реализаций, а не требование абстрагировать
каждую похожую строку.

**Последствия.** Можно исправить неиспользуемую ветку или случайно вернуть
старую логику при добавлении новой страницы. Текущий пользовательский дефект
от этих модулей не утверждается: consumers не найдены, поэтому приоритет низкий.

**Исправление на frontend.** После контрольного поиска потребителей удалить
неиспользуемые реализации и их реэкспорты, сохранив действующие `useProductForm`,
компоненты widget и AddToCartButton. Если ExternalPurchaseButton намеренно
оставлен для подтверждённого отдельного сценария, явно отделить этот сценарий
и его название от обычного `EXTERNAL_PRODUCT`; наличие такого сценария текущим
кодом не подтверждено. Новый универсальный form framework не нужен.

## 4. Области без серьёзных проблем

| Область | Оценка |
| --- | --- |
| Направление слоёв | В проанализированном локальном графе нет imports из shared/entities/features/widgets в верхние слои |
| Cross-feature / cross-widget | Между разными слайсами этих слоёв imports не найдены; композиция административных widgets передаётся через slots из app |
| Public API | Межслайсовых обходов внутренних файлов entities/features/widgets не найдено; `server.ts` и `@x` учтены как отдельные entry points |
| Межслайсовые entities | Связи идут через явные `@x`; соответствуют документированному исключению. Автоматически переносить эти связи в shared не следует |
| Циклы между слоями/слайсами | Не найдены; подтверждённые циклы A4 находятся внутри cart и favorite |
| HTTP и session | Общие clients используются из shared; session регистрируется через adapter в app. Обратного импорта session в Axios нет |
| Domain/UI | Модели товара, заказа, API и базовые правила в entities; checkout и order-create разделены на композицию и сценарную оркестрацию |
| Переиспользование товара | ProductCard принимает actions slot; catalog использует существующие features. Seller/admin редакторы разделены по подтверждённым сценариям |
| Размер модулей | Большие theme и UI-модули сами по себе не признаны дефектом; необоснованное дробление не рекомендуется |

Не все повторения заслуживают отдельной проблемы. Например, одинаковая
композиция покупательской карточки в ProductCatalog и RelatedProductsGrid
и расчёт диапазона цен в нескольких витринах дают небольшую стоимость
поддержки, но подтверждённого расхождения бизнес-правил в них не найдено.
При фактическом расширении этих сценариев можно выделить общий компонент
с действиями на разрешённом нижнем слое, не связывая widgets друг с другом.

Корневой `app/` не входит в Steiger — это явно документированное решение,
компенсируемое ручным review. SellerPageClient и login/register clients
содержат больше сценарной логики, чем тонкие route wrappers, но отсутствие
переиспользования этих экранов сейчас не обосновывает отдельный перенос
ради расположения файлов. При повторном использовании verification workflow
имеет смысл выделять именно его model, а не вводить обязательный слой pages.

## 5. Расширяемость

**Добавление нового функционала.** Структура не создаёт общего архитектурного
блокера. Существуют понятные точки для entity API/model, feature-действий,
widget-композиции и Next.js route. AdminAgentDetails демонстрирует возможность
собирать независимые widgets через slots без нарушения направления импортов.
Главный риск для любого нового приватного сценария — A1: каждый новый модуль
с пользовательским состоянием увеличивает число мест, которые надо очищать
при смене аккаунта. Эта граница должна быть общей до расширения таких сценариев.

**Новые сценарии работы с товарами.** Чтение и карточки переиспользуются,
actions slot позволяет добавлять действия без импорта features в entity.
Общий model формы уже покрывает seller create/edit; отдельный admin editor
обоснован иной ролью и существующим контрактом внешних товаров. Принудительно
объединять эти редакторы не рекомендуется.

Перед новым сценарием редактирования важно устранить A2: переиспользуемое
обновление товара не должно неявно означать физическое удаление файлов.
A5 затрудняет выбор действующей точки расширения, а A3 заставляет новые
гостевые действия наследовать неполную auth-навигацию. Эти ограничения
устраняются локальными изменениями frontend; новые backend-поля или статусы
для них не требуются.

Рекомендуемый порядок: A1 → A2 → A3; A4 и A5 — отдельная небольшая очистка.
Массовый перенос widgets в features, переписывание DTO во view models для всех
сущностей или смена frontend-стека не обоснованы результатами этого аудита.
