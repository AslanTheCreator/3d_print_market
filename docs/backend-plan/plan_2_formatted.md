# План доработок фронтенда: заказы, обращения и розыгрыши

## 1. Изменения существующей логики

### 1.1. Заказы и их статусы

1. **Добавить статус `CANCELLED`** во все списки заказов, детали, историю и фильтры. Теперь это обычная отмена заказа; `FAILED` остаётся отдельным итогом спора в пользу покупателя. Миграция также переводит часть исторических заказов из `FAILED` в `CANCELLED`.

2. **Обработать статус `DISPUTED`.** Показывать, что по заказу идёт разбирательство, и блокировать обычные действия, которые уже не соответствуют текущему статусу. После решения администратора обновлять данные заказа и обращения.

3. **Изменить прямую отмену заказа:**
   - Старый запрос: `POST /order/{orderId}/FAILED`.
   - Новый запрос: `POST /order/{orderId}/CANCELLED`.
   - В теле запроса больше не нужен `orderId`; остаются `closureReason` и `comment`, причём текущая реализация использует именно `comment`.
   - Прямая отмена доступна только для заказа в статусе `BOOKED`.

4. **Удалить старое закрытие спора** через `POST /order/orders/{orderId}/dispute/COMPLETED`. Теперь спор завершает администратор через обращение.

5. **Проверить экран подтверждения оплаты.** Если заказ перешёл в `DISPUTED` из `AWAITING_PAYMENT`, покупатель всё ещё может отправить подтверждение через существующий `POST /order/{orderId}/ASSEMBLING`. Оно добавляется к открытому спору, а статус остаётся `DISPUTED`. Это отдельное состояние интерфейса, не обычный переход к сборке.

### 1.2. Товары и изображения

1. **Обновить клиентские типы:** в `ProductAvailabilityType` добавлен `GIVEAWAY`, в `ProductStatus` — `AWAITING_GIVEAWAY`. Для обычного пользователя тип розыгрыша не должен появляться в форме создания товара: сервер разрешает его администратору.

2. **Не открывать розыгрыш** через обычный `GET /product/{id}`: этот endpoint исключает `GIVEAWAY`. Для розыгрышей предусмотрен отдельный публичный API.

4. **Не показывать удаление уже загруженных изображений заказа:** `DELETE /images` для `tag=ORDER` запрещён. До отправки файлов их можно удалять из локального предпросмотра.

## 2. Обращения по заказам

### 2.1. Интерфейс покупателя и продавца

Добавить в детали заказа блок **«Обращения»** с историей по `GET /order/{orderId}/cases`.

Ответ содержит массив `OrderCaseDetail`: объект `orderCase`, текущий `orderStatus`, участников, суммы, `paymentProofImageId`, `orderImages` и `caseImages`.

В карточке обращения показывать тип, автора, причину, дату, состояние, ссылку на Telegram, а после решения — исход и комментарий администратора.

#### Действия пользователя

| Действие | Когда доступно | Запрос | Результат |
|---|---|---|---|
| **Открыть спор** | Покупателю или продавцу после заявленной оплаты и при наличии подтверждения оплаты | `POST /order/orders/{orderId}/DISPUTED?comment=...&imageIds=...` | Заказ — `DISPUTED`, обращение — `OPEN` |
| **Попросить отменить неоплаченный заказ** | Покупателю или продавцу в допустимых неоплаченных состояниях | `POST /order/{orderId}/cancellation-request?comment=...` | Обращение — `OPEN`; статус заказа пока не меняется |
| **Сообщить об оплате после отмены** | Только покупателю для `CANCELLED` | `POST /order/{orderId}/payment-appeal?comment=...&imageIds=...` | Заказ — `DISPUTED`, обращение — `OPEN` |

#### Правила создания обращений

- `comment` обязателен во всех трёх случаях.
- Для доказательств сначала загрузить файлы через `POST /images?tag=ORDER&entityId={orderId}`, затем передать полученные ID как `imageIds`.
- Запрос отмены доказательств не принимает.
- После создания обращения повторно загрузить заказ и список обращений.
- Для одного заказа одновременно допускается только **одно открытое обращение**. Конфликт следует объяснять пользователю и обновлять экран.

**Основание:** [OrderCaseService.java (строка 50)](C:/Users/skura/IdeaProjects/model-store/src/main/java/com/model_store/service/impl/OrderCaseService.java:50).

> **Важно для интерфейса:** открытый запрос на отмену не виден по `actualStatus` заказа — статус не меняется. На странице заказа состояние нужно брать из `GET /order/{orderId}/cases`.
>
> Запрашивать обращения для каждой строки большого списка заказов может быть дорого. Если значок обращения нужен прямо в списке, лучше сначала добавить признак открытого обращения в ответ списка заказов на бэкенде.

### 2.2. Панель администратора

Добавить **очередь обращений** со следующими запросами:

| Метод и endpoint | Назначение |
|---|---|
| `GET /admin/actions/order-cases?state=OPEN&limit=50&offset=0` | Список `OrderCaseSummary`. Вкладки `OPEN` и `RESOLVED`, пагинация; `limit` от 1 до 100. |
| `GET /admin/actions/order-cases/{caseId}` | Детали `OrderCaseDetail`, включая участников, суммы и изображения. |
| `PUT /admin/actions/order-cases/{caseId}/telegram-url?url=...` | Прикрепление ссылки обсуждения. Допускается HTTPS-ссылка `t.me` или `telegram.me`. |
| `POST /admin/actions/order-cases/{caseId}/resolve?outcome=...&comment=...` | Принятие решения с обязательным комментарием. |

#### Возможные решения

Форму решения строить **по `orderCase.kind`**, а не по общему списку всех значений enum.

| Тип обращения | Доступные решения | Результат для заказа |
|---|---|---|
| `CANCELLATION_REQUEST` | `CANCELLED`, `REJECTED` | Отмена заказа либо сохранение текущего статуса |
| `DISPUTE` | `BUYER`; `SELLER` — только если спор открыт из `ON_THE_WAY` | `FAILED` либо `COMPLETED` |
| `PAYMENT_APPEAL` | `BUYER`, `SELLER` | В обоих случаях заказ возвращается в `CANCELLED`; исход фиксирует решение по обращению |

**Дополнительные ограничения:**

- `LEGACY` может встретиться у перенесённых старых споров, но отправлять его при новом решении нельзя.
- `state` и `outcome` в JSON выглядят строками, однако их набор ограничен enum; клиенту нужны соответствующие типы и подписи.
- Администратор проводит возможный возврат самостоятельно через прикреплённое обсуждение в Telegram. API автоматического возврата в этих коммитах нет.

## 3. Розыгрыши

### 3.1. Публичная часть

1. **Добавить блок или страницу розыгрыша** на основе `GET /giveaways/active`. Несмотря на имя, запрос возвращает также ближайший запланированный розыгрыш; его `status` будет `AWAITING_GIVEAWAY`. Если подходящего розыгрыша нет, сервер отвечает `404` — это нормальное пустое состояние.

2. **Добавить страницу по прямой ссылке** через `GET /giveaways/products/{productId}`. Она доступна для включённого розыгрыша до `endAt`; после окончания или отключения запрос вернёт `404`.

3. **Показать информацию о розыгрыше:** изображения, описание, `homeText`, `rules`, число победителей, даты и ссылку `telegramUrl`. Для запланированного розыгрыша показывать время до старта, для идущего — до завершения. Участие происходит по ссылке Telegram: в этих коммитах нет API регистрации участников или выбора победителей.

4. **Обновлять данные** при открытии страницы и на границах `startAt` / `endAt`. Сервер вычисляет публичную доступность по датам при запросе; постоянный опрос каждые несколько секунд не требуется. После завершения нужно перейти в состояние «розыгрыш окончен» или убрать блок после повторного запроса.

### 3.2. Панель администратора

1. **Расширить форму создания товара.** Для `availability=GIVEAWAY` добавить вложенный объект `giveaway` с полями:
   - `enabled`
   - `telegramUrl`
   - `startAt`
   - `endAt`
   - `winnersCount`
   - `rules`
   - `homeText`

   Даты отправлять как ISO 8601 с часовым поясом. Проверять Telegram URL, условие `startAt < endAt`, положительное число победителей и заполненные тексты.

2. **Добавить управление розыгрышами:**
   - `GET /admin/actions/giveaways/history?page=0&size=50`
   - `GET /admin/actions/giveaways/{productId}`
   - `PUT /admin/actions/giveaways/{productId}`

   История включает запланированные, идущие, завершённые и отключённые записи. Ответ деталей содержит `product`, `imageIds`, `categories`. `PUT` принимает объект настроек `giveaway` без дополнительной обёртки.

3. **Отображать `giveawayEnabled` отдельно от статуса.** При `enabled=false` публичный розыгрыш скрывается. При повторном включении дата окончания должна оставаться в будущем. Пересекающиеся периоды включённых розыгрышей сервер отклоняет — такую ошибку стоит выводить рядом с датами.

4. **Поддержать перевод товара бота в розыгрыш**, если в панели уже есть его редактирование, через существующий `PUT /admin/actions/agents/{agentId}/products/{productId}`. Администратор также может создать собственный товар-розыгрыш через `POST /products`.

## 4. Порядок реализации и проверки

1. **Контракты и существующие экраны.** Обновить клиентские enum, подписи статусов, отмену заказа, обработку изображений заказа и убрать старое закрытие спора.

2. **Обращения пользователя.** Добавить блок истории в заказе, три формы открытия обращения, загрузку доказательств и обновление состояния после отправки.

3. **Очередь администратора.** Реализовать список, детали, Telegram-ссылку и форму решения с вариантами по типу обращения.

4. **Розыгрыши.** Реализовать публичный блок и страницу, затем создание и управление в панели администратора.

5. **Проверка сквозных сценариев.** Проверить:
   - отмену заказа в `BOOKED`;
   - запрос отмены с решением и отказом;
   - спор с обоими допустимыми исходами;
   - оплату после отмены;
   - розыгрыш до старта, во время, после окончания и при отключении;
   - доступ к изображениям под разными ролями.

### Вопросы по API перед реализацией

> **1. Недостаточно данных в списке заказов.** Фронт сейчас не получает в `FindOrderResponse` признак открытого обращения и `paymentProofImageId`. Поэтому он не сможет точно показать все доступные действия и статус запроса отмены без дополнительного запроса на каждый заказ.
>
> **2. Нестандартный путь открытия спора.** Фактический endpoint содержит двойное `/order/orders/...`. Его следует использовать как есть либо отдельно исправить на бэкенде с согласованным изменением клиента.
