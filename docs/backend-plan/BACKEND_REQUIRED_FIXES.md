## BE-12-01. Разрешить X-Refresh-Token в CORS

**Классификация:** BACKEND CORS BUG, влияет на реальный frontend.
**Образ:** `ready555/model_store:v1.36`. **Результат:** CORS FAIL; успешный
браузерный `401 → refresh → retry` с сохранением ввода — BLOCKED.

### Фактическое поведение и воспроизведение

Живой OpenAPI требует `POST /auth/refresh` с обязательным header
`X-Refresh-Token`, без обязательного тела. Frontend выполняет именно этот запрос
напрямую из браузера к `http://localhost:8081`. `/api/config` только возвращает
адрес API; Next.js proxy и серверного refresh в приложении нет.

27.10.2026 в настоящем Chromium 148.0.7778.96, Next.js dev на
`http://localhost:3000`, без API mocks воспроизведён штатный interceptor:

1. Вход существующей DEV-учётной записью успешен; исходный access token принят
   `GET /auth/profile` (200).
2. Только в отдельном тестовом браузерном контексте access cookie заменена на
   недействительный token; действительный refresh token сохранён. API-ответы,
   код и конфигурация не подменялись.
3. Открытие истории существующего заказа вызывает настоящий
   `GET /order/159/cases` → 401; также `/auth/profile` возвращает 401.
4. Interceptor инициирует POST refresh; Chromium автоматически выполняет:

   ```http
   OPTIONS /auth/refresh HTTP/1.1
   Host: localhost:8081
   Origin: http://localhost:3000
   Access-Control-Request-Method: POST
   Access-Control-Request-Headers: x-refresh-token
   ```

5. OPTIONS получает **403**, `Access-Control-Allow-Origin` отсутствует.
   Chromium сообщает `net::ERR_FAILED` / `PreflightMissingAllowOriginHeader`;
   POST не отправляется после отказа preflight. Новый access token не получен,
   повтор исходного запроса не выполняется, обе auth cookies очищаются,
   приложение переходит на `/auth/login`.

Контроль с origin страницы Swagger `http://localhost:8081` прошёл: POST refresh
200, ответ `text/plain`, новый access token принят `/auth/profile` (200) для той
же учётной записи. OPTIONS отсутствует, поскольку запрос same-origin. Успех
Swagger не подтверждает работоспособность cross-origin browser refresh.

**Первопричина:** прочитанный из JAR запущенного контейнера `CorsConfig` содержит
разрешённые headers `Authorization`, `Content-Type`, `X-Requested-With`, но не
`X-Refresh-Token`. Контрольный OPTIONS на том же endpoint с теми же origin/POST
даёт 200 для каждого из трёх разрешённых headers и 403 для `x-refresh-token`.
Compose передаёт `APP_CORS-ALLOW-ALL=false` и
`APP_ALLOWED-ORIGINS=http://localhost:3000`: origin разрешён, список headers
этими параметрами не исправляется. Это рабочий сценарий приложения, а не
неиспользуемая диагностическая проба и не ошибка frontend-контракта.

### Ожидаемый результат и действия backend

Добавить `X-Refresh-Token` в разрешённые headers действующей CORS-конфигурации
для `/auth/refresh`, сохранить разрешённый origin и обработку preflight без
требования токена в OPTIONS. Endpoint продолжает принимать token в header и
возвращать access token строкой. Контракт frontend не менять; временные proxy,
mock-ответы и обходы browser CORS не добавлять.

### Минимальные критерии проверки

- OPTIONS выше возвращает успешный ответ (200 по текущему контрактному тесту),
  `Access-Control-Allow-Origin: http://localhost:3000`, разрешённые POST и
  `X-Refresh-Token`. Проверка не требует значения refresh token.
- В настоящем браузере без mocks защищённый запрос получает 401, затем фактически
  отправляются POST refresh и повтор исходного запроса с новым access token.
  Повтор успешен; учётная запись, сессия и введённые данные сохраняются.
- Конкурентные 401 используют один refresh; недопустимый origin отклоняется.
  Ошибка/невалидный refresh завершает сессию без бесконечных повторов.
- Прямой refresh и `/auth/profile` остаются успешными; секреты не появляются
  в диагностике. Повторить real-набор и записать версию/digest исправленного
  образа. FAIL/BLOCKED менять только по фактическим результатам.

## BE-12-02. Централизованная redaction HTTP-диагностики

**Классификация:** BACKEND LOGGING BUG.
**Образ:** `ready555/model_store:v1.36`. **Результат:** FAIL отдельного read-only
аудита. Frontend-сериализатор ошибок не устраняет запись серверных HTTP-логов.

### Фактическое поведение и воспроизведение

При интеграционных операциях со своими DEV-заказами синтетический комментарий
передавался через предусмотренный контрактом query, например:

```http
POST /order/{orderId}/cancellation-request?comment={synthetic-comment}
POST /admin/actions/order-cases/{caseId}/resolve?outcome=REJECTED&comment={synthetic-comment}
```

Placeholder не является реальным значением. Read-only аудит Docker logs в памяти
подтвердил сохранение query `comment` вместе со значением в HTTP request URI.
22.10.2026 13:56:05 UTC обнаружена 451 строка с синтетическим комментарием;
сохранены только обезличенные счётчики (`.cache/backend-stage12/logging-audit.json`).
Сами строки, комментарии и содержимое evidence не экспортировались.

JWT-подобные строки и query token/password/email в этой выборке не обнаружены;
это не доказывает безопасность остальных логов. Приватные сведения обращений
становятся доступны читателям серверных логов и агрегатора.

### Ожидаемый результат и действия backend

Внедрить централизованную redaction до записи и экспорта application/access/error
logs: исключить чувствительные query-параметры, включая комментарии, токены,
evidence, private payload и чувствительные headers. Не ограничиваться отдельным
контроллером или frontend-диагностикой. Сохранить безопасные method, route,
status, машинный code и correlation ID. Оценить доступ и retention уже записанных
логов. Перенос query в body требует отдельного согласования API-контракта и сам
по себе не заменяет redaction.

### Минимальные критерии проверки

- На разрешённом DEV выполнить успешную и отклонённую операции с новыми
  синтетическими маркерами, включая URL-encoded вариант; проверить обращения
  пользователя и административное решение.
- В application/access/error logs и экспортируемой диагностике отсутствуют
  исходные, декодированные и encoded чувствительные значения; маскирование
  выполняется до передачи в log sink/агрегатор. Есть серверные регрессии.
- Безопасные method/route/status и идентификаторы корреляции сохранены;
  последующий GET подтверждает обычный бизнес-результат операции.
- Зафиксировать только счётчики и безопасные идентификаторы, версию/digest
  исправленного образа. Текущий FAIL сохраняется до такого подтверждения.
