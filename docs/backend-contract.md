# Backend: production-согласования

Документ не является подтверждённым API-контрактом. Он фиксирует текущую зависимость frontend и решения, которые нужно согласовать с backend до production.

## Текущая реализация

Источник истины — API-модули в `src/shared/api` и `src/entities/*/api`.

Auth сейчас использует bearer tokens:

- **`POST /participant`** — `{ mail, password, age }`, в ответе ID пользователя.
- **`POST /auth/login`** — access и refresh tokens.
- **`POST /auth/verification/resend`** — ID пользователя; cooldown обрабатывается по `429`.
- **`POST /auth/verify-code`** — access и refresh tokens.
- **`POST /auth/refresh`** — refresh token в `X-Refresh-Token`, новый access token в ответе.
- **`POST /auth/password/reset`** — email в query params.

Контракт корзины backend v1.28:

- **`POST /basket/find`** — каждая `ProductBasketDto` содержит `availableCount: number | null` и `enoughStock: boolean`.
- **`PUT /basket`** — успешный ответ `200` без body; после него frontend повторяет `POST /basket/find`.

`availableCount` — текущий доступный остаток; `null` означает отсутствие ограниченного остатка. `enoughStock` — серверное решение о достаточности остатка для текущего количества в корзине и имеет приоритет над вычислениями frontend.

Zustand хранит оптимистичное количество для мгновенной синхронизации UI, но подтверждённые количество и остаток берутся из повторного ответа backend. Frontend не уменьшает количество автоматически: при ошибке изменения выполняет rollback, а при ошибке контрольного запроса требует retry. Недостаточный остаток, ожидающее подтверждения количество или непроверенные данные блокируют checkout только для выбранных позиций.

Контракт товаров, сверенный с локальным OpenAPI и публичными ответами 28.09.2026:

- **`POST /products/find`, `GET /product/{id}`** — публичные ответы скрывают `externalUrl` значением `null`; `count=null` означает неограниченный остаток. OpenAPI пока не отражает nullable-поля.
- **`FindProductRequest`, `FindMyProductRequest`** — поле `imageId` отсутствует и frontend его не отправляет.
- **`POST /products/find`** — `includeAdult` отсутствует; необязательный `Authorization` определяет возрастной доступ. Без валидного токена выдача не содержит 18+.
- **`EXTERNAL_PRODUCT`** заменяет `EXTERNAL_ONLY` и допускается в обычном сценарии корзины и заказа согласно PLAN.md; `PRODUCT_NOT_PURCHASABLE` по-прежнему обрабатывается как отказ без внешнего перехода.

`EXTERNAL_PRODUCT` покупается через marketplace. Нулевые и истёкшие товары исключает из публичного каталога backend; в `POST /products/my` товар с нулевым остатком ожидаем и отображается продавцу.

Frontend рассматривает `EXTERNAL_PRODUCT` как read-only тип в обычном кабинете продавца. Create/update model допускает только `PURCHASABLE` и `PREORDER`; edit, delete и extend для внешнего товара здесь недоступны. Это не заменяет backend authorization и проверку происхождения записи. Административное управление ботами является отдельным сценарием.

Checkout вызывает `POST /order/BOOKED` отдельно для каждой позиции и ожидает массив ID заказов. `Idempotency-Key` пока не отправляется.

## Обязательные согласования

### Auth

Целевое production-решение — HttpOnly cookies, но оно внедряется только после подтверждения backend.

Нужно согласовать:

- login, verify, refresh и logout;
- cookie names, scope, `Secure` и `SameSite`;
- CSRF-защиту;
- CORS и credentials для local/test/production;
- способ server-side проверки сессии для protected routes;
- миграционное окно для bearer-схемы.

После готовности backend frontend должен убрать JS-readable tokens, `Authorization` interceptor и `X-Refresh-Token`, включить credentials и добавить server logout.

Также требуется согласовать:

- `PUT /participant/password` с паролями в JSON body, а не в query string;
- password reset без account enumeration: единый публичный ответ, rate limit, single-use, expiry и отзыв активных сессий;
- централизованный session teardown для явного logout, refresh failure и server-side invalidation;
- TTL access token через подтверждённый `exp`/`expires_in`, а не разные frontend constants;
- redaction password, tokens, cookies и authorization headers в proxy/backend logs.

### Checkout

Backend должен гарантировать идемпотентность создания заказа. Краткое предложение: [backend-checkout-idempotency.md](./backend-checkout-idempotency.md).

Отдельно нужно согласовать:

- остаётся ли запрос по одной позиции или вводится атомарная группа продавца;
- как доставка применяется к группе;
- формат частичного успеха;
- стабильные business error codes;
- запрет покупки собственного товара на стороне backend.

Frontend-проверка собственного товара остаётся только UX-защитой и не заменяет серверную проверку.

Комментарии заказа, tracking/delivery URL и другие пользовательские значения сейчас передаются частью endpoints через query params. Целевой контракт должен переносить чувствительные и длинные значения в JSON body и ограничивать их размер/формат.

### Юридическое уведомление при регистрации

Frontend показывает под формой регистрации ссылки на пользовательское соглашение и политику конфиденциальности без отдельного checkbox. Текущий `POST /participant` не передаёт версию документов и время принятия. Если потребуется хранить явный факт согласия, поля backend-контракта и соответствующий UI должны быть согласованы отдельно; до этого payload не расширяется.

### Статусы заказов

Frontend вызывает status endpoints из `src/entities/order/api/orderApi.ts`. Для этапов 1–5 используется следующая матрица:

| Этап | Кто выполняет | Исходное состояние | Условие по заказу | Результат |
|---|---|---|---|---|
| 1. Создание | Покупатель | — | `PURCHASABLE`, `PREORDER` или `EXTERNAL_PRODUCT` | `BOOKED` |
| 2. Подтверждение продавцом | Продавец | `BOOKED` | `prepaymentAmount = 0` | `AWAITING_PAYMENT` |
| 2. Подтверждение продавцом | Продавец | `BOOKED` | `prepaymentAmount > 0` | `AWAITING_PREPAYMENT` |
| 3. Оплата обычного заказа | Покупатель | `AWAITING_PAYMENT` | Без предоплаты | `ASSEMBLING` |
| 3.1. Предоплата | Покупатель | `AWAITING_PREPAYMENT` | С предоплатой | `AWAITING_PREPAYMENT_APPROVAL` |
| 3.2. Подтверждение предоплаты | Продавец | `AWAITING_PREPAYMENT_APPROVAL` | С предоплатой | `AWAITING_PAYMENT` |
| 3.3. Оплата остатка | Покупатель | `AWAITING_PAYMENT` | После предоплаты | `ASSEMBLING` |
| 4. Отправка | Продавец | `ASSEMBLING` | Любой покупаемый тип | `ON_THE_WAY` |
| 5. Получение | Покупатель | `ON_THE_WAY` | Любой покупаемый тип | `COMPLETED` |

На этапе 2 frontend вызывает одно текущее действие подтверждения. Backend должен сам выбрать `AWAITING_PAYMENT` или `AWAITING_PREPAYMENT` по наличию предоплаты в заказе; frontend не должен передавать или вычислять целевой статус. Для действий продавца по товарам ботов предусмотрен отдельный административный API из PLAN.md; его подключение относится к следующему этапу. Отмена и отзыв в эту матрицу не входят; пункты 6–7 открытия и завершения спора отложены.

Для каждого перехода backend должен атомарно проверить существование заказа, участника и его роль, актуальный статус, тип товара из snapshot и обязательные данные действия. В частности:

- этапы 3, 3.1 и 3.3 требуют валидный `imageId` подтверждения оплаты с tag `ORDER`;
- этап 3.2 доступен только продавцу этого заказа после предоплаты;
- этап 4 требует абсолютный tracking/delivery URL со схемой HTTP или HTTPS;
- повторный или конкурентный переход не должен перезаписывать уже принятое состояние.

OpenAPI должен описывать не только успешный `200`, но и стабильные ошибки для неверной роли, недопустимого перехода или конкурентного изменения, отсутствующего заказа и невалидных обязательных данных. Frontend ожидает нормализуемый business error и не добавляет новые коды до подтверждения backend.

### Snapshot и финансовая семантика заказа

Ответ заказа должен содержать неизменяемый snapshot данных, по которым заказ был создан. Последующее редактирование карточки товара, цены, предоплаты, доступности или доставки не должно менять историю и расчёты существующего заказа.

PLAN.md и текущий OpenAPI подтверждают верхнеуровневые суммы заказа. Frontend использует следующую модель:

- `product.count` в заказе — заказанное количество, а не текущий остаток товара;
- `order.prepaymentAmount` — предоплата за всё заказанное количество, `totalPrice` — остаток к оплате для любого типа товара;
- эти суммы не пересчитываются из `product.prepaymentAmount`, `product.price` или количества; полная стоимость товаров для отображения равна их сумме;
- `product.currency` относится ко всем суммам товара из snapshot;
- `transfer.price` и `transfer.currency` относятся к доставке, которая всегда показывается отдельно и не входит в `totalPrice`;
- если валюты товара и доставки могут различаться, backend не должен возвращать агрегированный итог без отдельно согласованного правила конвертации.

Неизменяемость snapshot и правила доставки/конвертации требуют серверной гарантии. Поля сумм не включаются в запрос создания заказа.

### Остаток предзаказа

Backend должен определить и документировать момент резервирования, списания и освобождения остатка `PREORDER`, включая отмену, timeout, конкурентные checkout-запросы и истечение резерва. Серверный остаток остаётся источником истины: frontend не уменьшает и не восстанавливает его локально после создания или перехода заказа.

### Даты заказа

`createdAt` и `histories.changedAt` должны возвращаться в ISO 8601 с timezone. Временная поддержка frontend формата `DD.MM.YYYY HH:mm:ss` нужна только для совместимости с текущими ответами и не является целевым контрактом. Сортировка истории должна опираться на тот же момент времени, который отображается пользователю.

### Изображения

`GET /images?ids=...` не позволяет надёжно сопоставить batch-ответ, если элементы не содержат ID и порядок не гарантирован. Сейчас frontend запрашивает несколько изображений по одному.

Для безопасного batch frontend нужен один подтверждённый вариант:

- порядок ответа совпадает с порядком `ids`; или
- каждый элемент ответа содержит ID изображения.

Изображения с tag `ORDER` являются подтверждениями оплаты и не могут использовать общий публичный read contract. Нужно подтвердить:

- object-level authorization: читать может только допустимый участник конкретного заказа;
- private bucket/object ACL либо короткоживущий signed access;
- отсутствие доступа перебором image ID;
- server-side проверку content type, сигнатуры, размера и безопасного декодирования;
- атомарную привязку proof к конкретному заказу вместе с успешным переходом этапа 3, 3.1 или 3.3;
- запрет повторной привязки proof к чужому заказу и удаления уже привязанного изображения;
- удаление orphan uploads и явно заданную retention policy.

Frontend upload выполняется через `authClient`, но чтение сейчас использует общий `publicClient`; миграция read path обязательна после готовности контракта. При отклонённом переходе загруженный `imageId` должен оставаться пригодным для безопасного retry того же действия. При timeout с неизвестным результатом frontend сначала перечитывает заказ и не удаляет upload, пока backend-состояние не подтвердит, что proof не был привязан.

### Платёжные реквизиты

Frontend получает `entityValue` продавца по `participantId`. До production backend должен выбрать и подтвердить один вариант:

- реквизиты доступны только стороне конкретного заказа через order-scoped endpoint; или
- отдельно определённый набор реквизитов является публичным, а чувствительные поля никогда не входят в него.

Одна проверка авторизации без object-level связи пользователя, заказа и продавца недостаточна.

Выбор реквизита в текущем frontend нужен только для явного UX при нескольких счетах. `accountId` не входит в status payload и не должен добавляться без отдельно подтверждённого контракта.

### Adult content

Backend и frontend должны использовать один подтверждённый признак adult category/product. Требуется определить:

- публичные list/search/seller/related responses исключают adult products по умолчанию;
- возрастная фильтрация `POST /products/find` определяется авторизованной сессией без `includeAdult`;
- detail endpoint возвращает достаточно данных для единообразного gate и не раскрывает media до подтверждения;
- sitemap/feed endpoints не включают adult products, если они не должны индексироваться;
- правила применяются также к favorites и старым позициям cart.

Сейчас frontend gate существует только в category flow, поэтому одним backend-фильтром category list проблема direct detail не закрывается.

### Внешние ссылки товаров

Публичный UI не показывает `externalUrl`. Политика проверки внешних URL потребуется для административного редактора товара бота, а не для покупательского перехода.

### Управление товарами внешнего источника

Публичные frontend endpoints не должны управлять товарами, которые поступают из доверенного import/sync-контура. Backend должен:

- отклонять создание товара с `availability: EXTERNAL_PRODUCT` через обычный пользовательский API;
- запрещать преобразование обычного товара в `EXTERNAL_PRODUCT` через публичный create/update contract;
- отклонять update существующего внешнего товара независимо от `availability` в новом payload;
- отклонять delete и extend внешнего товара;
- принимать изменения таких записей только из доверенного import/sync-контура или административного API с проверкой прав;
- возвращать согласованный стабильный business error без раскрытия внутренних данных интеграции.

Update-проверка должна использовать сохранённое происхождение товара. Одной проверки входящего `availability` недостаточно: клиент способен подставить `PURCHASABLE` и попытаться обойти ограничение. Если `availability` не является надёжным неизменяемым признаком происхождения, backend должен хранить отдельный server-controlled признак; его точное имя и формат требуют согласования.

### Ошибки и rate limits

Backend должен согласовать единый формат business errors и cooldown для чувствительных auth/order операций. Для order flow этапов 2–5 OpenAPI должен отдельно описать:

- отказ по роли или object-level authorization;
- отсутствующий либо недоступный заказ;
- конфликт текущего статуса, включая конкурентный переход;
- невалидный или недоступный payment proof;
- невалидный tracking/delivery URL;
- временную серверную ошибку.

Точное соответствие HTTP status и business code требует подтверждения; как минимум frontend должен различать `403`, `404`, `409`, validation response и `5xx`. Frontend не добавляет новые коды и статусы до подтверждения.

## Готовность к frontend-миграции

Миграция начинается, когда на test/staging подтверждены:

- auth cookies, refresh, logout, CSRF и CORS;
- server-side session check;
- идемпотентное создание заказа без дублей при retry и параллельных запросах;
- условный результат подтверждения `BOOKED` по сохранённой предоплате;
- подтверждённая семантика количества, сумм товара, предоплаты, остатка, валюты и доставки;
- lifecycle остатка `PREORDER`;
- ISO 8601 даты заказа и истории с timezone;
- обязательная атомарная привязка приватного payment proof к этапам оплаты;
- серверный запрет покупки собственного товара;
- серверный запрет create/update/delete/extend для товаров внешнего источника;
- согласованные error codes и response shapes.
