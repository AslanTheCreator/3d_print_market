# API и auth

## Типы интеграции обращений и розыгрышей

Этап 1 добавил DTO в public API `entities/order` и `entities/product`.
Подтверждённые поля, ответы B1–B4/N1–N2 и расхождения OpenAPI v1.36 от 15.10.2026
и бизнес-правила первоисточника описаны в
[контрактах интеграции](./backend-integration-contracts.md).
Подключены чтение/создание пользовательских обращений и рассмотрение ADMIN;
API розыгрышей пока не подключены. Seller payload по-прежнему
исключает GIVEAWAY; административный wire-тип отделён от обычной формы.

## Отмена заказа (этап 2)

Прямая отмена покупателя и продавца разрешена только в BOOKED. `orderApi.cancelOrder`
принимает orderId отдельно от `OrderCancel`: `POST /order/{orderId}/CANCELLED`
получает JSON `{ closureReason, comment }`, без orderId. UI объединяет причину
и дополнительный текст в comment; отправку блокируют актуальный статус,
ошибка чтения списка и выполняющаяся операция.

После подтверждённого POST перечитываются scoped списки обеих ролей. Ошибка
обновления списка отображается отдельно и не превращает принятую отмену в отказ.
После ошибки POST feature отменяет прежний GET и выполняет контрольное чтение
списка текущей роли, без использования staleTime. Ввод сохраняется.
Подтверждённый 4xx (кроме 408) разрешает повтор только после успешного GET с BOOKED.
При потере ответа/5xx прежний BOOKED или отсутствие заказа не доказывает отказ:
повтор POST блокируется, доступна проверка GET. CANCELLED подтверждает итог;
иной актуальный статус блокирует прямую отмену.

Guard отмены (`busy`, принятый результат, recovery) и ввод формы разделяются
всеми кнопками одного заказа через существующий QueryClient: ключ
`["private", scopeId, "orderCancel", orderId]`, disabled query без сетевого чтения
и с gcTime=Infinity. Закрытие, смена фильтра и unmount не сбрасывают незавершённую
операцию; поздний ответ обновляет её независимо от прежней формы. UI-callback
выполняется только для актуальной формы. Неопределённый результат остаётся
заблокированным после GET BOOKED, включая повторное открытие и другие кнопки.
Подтверждённый отказ и последующий GET BOOKED разрешают только явный повтор.
Guard не дублирует DTO заказа; источник статуса — scoped список. Выход, истечение
сессии и смена аккаунта удаляют guard и ввод через PrivateDataBoundary; refresh
того же аккаунта сохраняет их. Поздний ответ старого scope не восстанавливает
удалённую запись. Состояние хранится только в памяти данного QueryClient,
без browser storage и гарантий между вкладками или после полной перезагрузки.

`getCustomerOrderActionFlags` / `getSellerOrderActionFlags` отделены от
`getAdminOrderActionFlags`. По окончательному B4 ADMIN CANCEL разрешён только
в BOOKED с результатом CANCELLED; остальные статусы запрещены. Правила
CONFIRM, CONFIRM_PREPAYMENT и SHIP сохранены. Перед CANCEL выполняется свежее
чтение заказа бота; проверяются BOOKED, sellerId, актуальность формы/scope
и результат существующей проверки доступа ADMIN после ожидания GET.
При ошибке GET POST не отправляется и ввод сохраняется; это не потеря ответа POST.
Административный
URL `/admin/actions/agents/{agentId}/orders/{orderId}/CANCEL`, query comment
и сверка неизвестного результата через список бота сохранены. Итоговый статус
берётся из серверного чтения; имя CANCEL не означает автоматически CANCELLED.

Состояние ADMIN CANCEL (busy, accepted, unknown, комментарий и результат проверки)
принадлежит существующему QueryClient: disabled query
`["private", scopeId, "adminOrderCancel", agentId, orderId]` с gcTime=Infinity.
Используется тот же подход, что у пользовательской отмены, без cross-feature
импортов и без пользовательского endpoint. Смена ADMIN → USER → ADMIN не меняет
scope и не сбрасывает guard. Выполняющийся/неопределённый запрос блокирует повтор
CANCEL во всех формах этого заказа; BOOKED и отсутствие заказа не доказывают отказ.
После восстановления ADMIN доступны состояние ожидания и проверка результата;
комментарий отправленного запроса восстанавливается. Отказ 4xx, кроме 408,
допускает явный повтор с прежней обязательной проверкой B4 перед POST;
network/timeout/5xx требуют восстановления через GET. Ошибка GET до начала POST
не помечается как неопределённый POST.

Поздний ответ сохраняется даже после unmount/отзыва роли, но callbacks старой
формы и новые административные чтения без ADMIN не запускаются. При подтверждённом
успехе повтор остаётся запрещённым даже при ошибке обновления списка. Logout,
expiry и смена аккаунта удаляют запись через PrivateDataBoundary; поздний ответ
старого scope не восстанавливает её. Хранение ограничено памятью QueryClient,
как у пользовательского guard. Только успешный ответ POST или GET CANCELLED
подтверждает CANCEL; иной статус после контрольного GET сохраняет unknown и guard
повторной отмены, а список обновляется фактическим статусом.

После завершения запроса unknown-форму CANCEL можно закрыть кнопкой «Закрыть»
или Escape. Закрытие сбрасывает только UI формы: guard, отправленный комментарий
и recovery остаются в private scope. При повторном открытии доступны GET-проверка
результата и прежний комментарий, повторный POST запрещён. Отправленный комментарий
при unknown/accepted не считается несохранённым вводом. Pending продолжает блокировать
закрытие и конкурирующие действия; GET BOOKED не подтверждает ни успех, ни отказ CANCEL.

CONFIRM/CONFIRM_PREPAYMENT/SHIP используют собственные состояния и прежнюю матрицу:
BOOKED, AWAITING_PREPAYMENT_APPROVAL и ASSEMBLING соответственно. Общий busy CANCEL
блокирует их до завершения запроса/контрольного чтения, включая submit из другого
экземпляра. Сохранённые accepted/unknown CANCEL сами по себе эти действия не
блокируют и не подменяют их feedback или проверку результата. Перед их POST
перечитывается заказ, проверяются статус, sellerId/orderId, текущий scope и ADMIN,
а также общий busy CANCEL после ожидания GET. Ошибка GET не считается потерей
ответа POST. CANCELLED не разрешает ни одно из этих действий.

В интерфейсе CANCELLED — «Отменён», FAILED — «Спор решён в пользу покупателя»,
DISPUTED — «На рассмотрении». Отменённые имеют отдельный фильтр; обычная цепочка
прогресса скрыта для этих трёх состояний. Исторический FAILED не преобразуется.
Старого пользовательского закрытия спора `/order/orders/{orderId}/dispute/COMPLETED`
в `src` нет; новый код его не вызывает.

## Изображения заказа (этап 3)

`imageApi.getOrderImages(ids, signal)` читает `GET /images?ids=...` через
authClient, без публичного fallback. `adminImageApi.read` переиспользует этот
транспорт; административный query остаётся в ветке `["admin", session, ...]`.
`useOrderImagesQuery` использует `["private", scopeId, "orderImages", orderId, ...ids]`
с уникальными положительными safe integer ID. Чтение не запускается без сессии,
принимает AbortSignal; при ручном refetch дополнительно проверяет актуальность
scope. staleTime/gcTime равны нулю: после закрытия приватная галерея не хранится
для повторного показа. Смена аккаунта/выход отменяют и удаляют эту ветку через
существующий PrivateDataBoundary. Metadata товаров остаётся публичной и отдельной.

`order.images` показываются обеим сторонам заказа как «Изображения заказа»,
с нейтральными alt и loading/error/empty. Статус, имя файла, порядок и пустая
история не определяют назначение изображения и не доказывают отсутствие чека.
Content type и base64 проверяются перед ImageGallery. Ответ ImageResponse
не содержит ID; отдельный payment proof на этапе 4 читается по известному ID,
без сопоставления по позиции массива.

PaymentDialog сначала хранит File и blob preview только в памяти. До отправки
файл можно заменить или удалить локально. Upload выполняется при submit через
`saveOrderImage(file, orderId, signal)`: multipart POST
`/images?tag=ORDER&entityId={orderId}`, поле `files`. Пустой массив и невалидные
ID отклоняются. После получения ID файл закреплён: ошибка status mutation
сохраняет его для повтора без нового upload; замена/удаление недоступны.
Закрытие, ошибка, размонтирование и смена scope не выполняют DELETE.
Blob URL освобождаются при замене/очистке/unmount. Поздний upload отменяется
и не меняет другую форму; перед status mutation повторно проверяются заказ,
scope, текущий статус, readiness списка и реквизиты.

`NonOrderImageTag` исключает ORDER из generic saveImage, deleteImages и
upload/cleanup hooks. Generic API дополнительно отклоняет ORDER во время
исполнения, до HTTP-запроса. Product/avatar upload и cleanup сохраняют прежний
flow. Серверная проверка object-level доступа остаётся обязанностью backend;
mock-тесты и чтение OpenAPI не подтверждают её выполнение на реальных данных.

## История обращений (этап 4)

`orderCasesApi.list(orderId, signal)` читает только `GET /order/{orderId}/cases`
через authClient. `useOrderCasesQuery` использует ключ
`["private", scopeId, "orders", "cases", orderId]`, staleTime/gcTime=0,
AbortSignal и повторное чтение при открытии/возврате фокуса. В списках заказов
запросов обращений нет: observer получает только выбранный заказ. Невалидный ответ
и явный чужой orderCase.orderId отклоняются как ошибка, а не пустая история.
Закрытие/смена заказа отменяют чтение; PrivateDataBoundary удаляет его при смене
аккаунта. Optional/null B2 paymentProofImageId и N2 currency сохраняются без defaults.

OPEN определяется по state. Ошибка истории с retry не скрывает контакты, историю
статусов и order.images и не доказывает отсутствие оплаты. При расхождении
orderStatus обращений со списком widget перечитывает существующий список роли:
до сверки действия этого orderId блокируются, в том числе после закрытия деталей. Ошибка чтения
или сохраняющееся расхождение требуют retry; автоматического цикла GET нет.
Отсутствующий orderStatus старого ответа не снимает ранее установленную блокировку.
Сохранённые ошибки, pending и retry адресованы orderId внутри текущего scope:
переход к другому заказу не переносит ограничения, а возвращение сохраняет их
до достоверной сверки. Действия строк списка также запрашивают recovery по своему
orderId. Поздний результат обновляет только свою сверку; более новый запуск,
размонтирование widget и смена аккаунта запрещают применение старого результата.
После закрытия деталей список сохраняет предупреждение и адресную кнопку retry
для каждого проблемного заказа, не блокируя действия остальных строк.
Мутации существующих заказов инвалидируют также активную историю обращений.

Общий нейтральный блок объединяет уникальные order.images и orderImages истории.
Положительные paymentProofImageId показываются отдельным чтением каждого известного
ID, поскольку ImageResponse не содержит ID для сопоставления batch-ответа.
Они исключаются из общих галерей; карточка сохраняет связь с чеком ссылкой на его
раздел, включая пересечение с caseImages. Остальные caseImages нейтральны и
показаны в карточке обращения. Пустая/ошибочная история, отсутствующий или null ID
не превращаются в сообщение об отсутствии подтверждения. В AWAITING_PAYMENT
чек может относиться к предоплате. Позиция и имя файла не используются.

## Создание обращений (этап 5)

`orderCasesApi.create` и `useCreateOrderCase` используют authClient и три отдельных
POST: `/order/{id}/cancellation-request`, `/order/orders/{id}/DISPUTED`,
`/order/{id}/payment-appeal`. Непустой comment передаётся в query; необязательные
imageIds — повторяющимися параметрами без скобок. Success DTO не предполагается.
Запрос отмены исключает imageIds и в TypeScript, и до HTTP-запроса.

`getAvailableOrderCaseKinds` применяет B1/B2 из
[контрактов](./backend-integration-contracts.md#b1b2-обращения-и-подтверждение-оплаты):
любой OPEN блокирует создание, прежний PAYMENT_APPEAL запрещает повторный appeal
даже после RESOLVED. Отсутствующий paymentProofImageId не равен null; images не
заменяет это поле. Неизвестное состояние обращения блокирует новые действия.
Принадлежность подтверждается наличием заказа в scoped списке текущей роли,
ID из профиля и доступными ID участников; sellerId отдельно проверяется у продавца.
Авторизация на уровне объектов остаётся обязанностью backend.

Feature `order-case-create` размещает три варианта React Hook Form в разделе
обращений деталей заказа. Перед upload/POST выполняется свежее чтение списка роли
и истории с отменой прежних GET, без staleTime/retry. После upload доступность
проверяется повторным чтением. Файлы необязательны и выбираются локально;
`saveOrderImage` вызывается только при submit. При частичном успехе полученные ID
сохраняются, повтор загружает только оставшиеся файлы. DELETE не выполняется.

Черновик и guard busy/accepted/unknown/rejected живут в памяти QueryClient под
`["private", scopeId, "orderCaseCreate", orderId]` с gcTime=Infinity. Это состояние
операции, без копии server DTO. Повторное открытие восстанавливает комментарий,
локальные File и ID; выход/смена аккаунта очищает их через PrivateDataBoundary,
refresh сохраняет. После unmount до POST цепочка останавливается; начатый POST
сохраняет результат для того же scope. Между вкладками и после reload guard не общий.

POST не повторяется автоматически. N1-коды разделены: ORDER_CASE_ALREADY_OPEN,
PAYMENT_APPEAL_ALREADY_EXISTS, ORDER_CASE_INVALID_TRANSITION, BAD_REQUEST,
INVALID_REQUEST; любой другой 409 не называется открытым обращением. После отказа
перечитываются заказ и история; явный повтор разрешается только при свежей допустимой
матрице. Неопределённый POST остаётся заблокированным до обнаружения нового обращения
с совпавшими видом, автором и комментарием относительно снимка до записи. Если ID
исходных обращений отсутствуют, новое обращение не считается доказанным. Сам по себе
прежний статус или пустая история не доказывают отказ. При успехе инвалидируются
оба scoped списка и история этого заказа; контрольное чтение обновляет текущую роль
и `/cases`. Ошибка этого GET не отменяет принятый POST: доступен повтор чтения,
создание заблокировано. Статус берётся только из GET; запрос отмены его не меняет.

## Подтверждение оплаты в споре (этап 6)

`entities/order.getDisputePaymentCase` разрешает действие только покупателю своего
`DISPUTED` из свежего списка `/order/customer`: ровно одно идентифицированное
`OPEN DISPUTE` с `previousOrderStatus=AWAITING_PAYMENT`. Неизвестные состояния,
расхождения участников/статусов и другой исходный статус блокируют запись.
`widgets/orders` передаёт контекст истории в `features/order-payment`;
`PaymentDialog` имеет отдельный режим `dispute`, без запроса счетов продавца.
Он сообщает об уже совершённой оплате через существующий приватный
`POST /order/{orderId}/ASSEMBLING?imageId=...&comment=...`, без JSON и accountId.
OpenAPI этого POST повторно прочитана 16.10.2026; поведение в DISPUTED задано
backend-требованиями, а не схемой. Статус локально не меняется.

Черновик и синхронный busy guard хранятся в памяти QueryClient под
`["private", scope, "disputePayment", orderId]`: исходный caseId, File, загруженный
imageId, комментарий, исход POST и результат проверки. Закрытие/remount сохраняет
их; refresh токена сохраняет scope, logout/expiry/смена аккаунта очищает его.
Дискового хранения и общего guard между вкладками или после reload нет.
Перед upload и непосредственно перед POST перечитываются заказ и `/cases`,
отменяя прежние GET и обходя staleTime; проверяется тот же caseId. Unmount до
POST останавливает цепочку, сохраняя полученный ID; начатый POST завершает recovery
в том же scope даже без компонента. Повторного upload сохранённого ID нет.
Offline-очередь и автоматические повторы отключены: восстановление сети не
отправляет отложенный POST после закрытия формы.

После POST инвалидируются оба списка роли и история только этого заказа,
перечитываются `/order/customer`, `/cases` и связанные scoped ORDER-изображения.
Успешный POST остаётся принятым при ошибке GET. Network/timeout/408/5xx дают
неопределённый исход и блокируют новый POST; отсутствие ID при чтении не означает
отказ. `hasDisputePaymentProof` подтверждает результат по отправленному imageId
в paymentProofImageId/caseImages исходного обращения, включая уже RESOLVED.
Один orderImages после upload и изменение статуса успех не доказывают.
После явного 4xx-отказа повтор возможен только по свежей допустимой матрице;
после неудачного контрольного GET сначала требуется явная проверка результата.

## Административный API

Форма `/auth/login` принимает email или непустой логин (например, административный).
Пробелы по краям удаляются; значение передаётся без изменения регистра в поле
`mail` запроса `POST /auth/login`. Проверка формата email при входе отключена
через `AuthForm.allowLoginIdentifier`; подпись «Email» и остальные тексты UI
сохранены, подсказка о входе по логину не отображается. Регистрация и восстановление
пароля по-прежнему проверяют формат email. Поддержка логина не меняет проверку
пароля на backend и требование роли ADMIN для доступа к административным страницам.

Вход использует общий auth flow. После него `useSessionProfile` отдельно читает
`/auth/profile` через authClient, без зависимости от загрузки аватара. Доступ к
`/admin` разрешён только при `role === "ADMIN"`; cached роль не подменяет первую
проверку после монтирования guard. До проверки дочерние запросы не запускаются.

После успешной проверки ADMIN ошибка фонового чтения профиля сохраняет уже
смонтированное admin-дерево и локальный ввод. `AdminAccess` показывает диалог error/retry
и блокирует взаимодействие, включая submit и действия в React portals, до
успешной повторной проверки. Начатые операции продолжают обработку результата.
Первоначальный отказ блокирует дерево; 401 завершает сессию, а подтверждённая
смена роли закрывает доступ. Retry с прежней ролью ADMIN не пересоздаёт редактор.

Административные query keys начинаются с `["admin", sessionKey, ...]`; параметры
бота/товара/заказа/фильтра входят в ключ. `PrivateDataBoundary` отменяет и удаляет
ключи предыдущей сессии при login/logout/смене аккаунта. `useAccountSessionKey`
использует неперсистентный accountRevision: обновление токена того же аккаунта
не уничтожает открытый ввод, а обычный sessionRevision для публичного поиска
сохраняет прежнее поведение. GET принимают AbortSignal;
данные форм и приватные изображения не персистятся в localStorage. Сервер
остаётся источником проверки полномочий для каждой операции.

- `agentApi`: GET списка и профиля, PUT пяти редактируемых полей профиля.
- `adminProductApi`: списки ботов, raw product и отдельные публичные связи;
  PUT выполняется только после сверки id/participantId и наличия categories/
  imageIds. availability фиксирован EXTERNAL_PRODUCT, externalUrl обязателен,
  count=null отличается от 0. Статус и продление — отдельные admin mutations.
- `adminOrderApi`: общий/scoped список по 50 и четыре POST actions. sellerId
  берётся из корня заказа; comment/deliveryUrl — query params. Корневые суммы
  используются без повторного умножения на количество, доставка отдельно.
  После timeout сначала выполняется поиск заказа в страницах бота без status;
  неизменившийся/не найденный статус не разрешает слепой повтор.
- Административные CRUD реквизитов, адресов, доставки и контактов находятся
  рядом с соответствующими entities. Только 404 ACCOUNT_NOT_FOUND нормализуется
  в пустой список. После успешной записи и неуспешного refetch повторяется GET.
  При потере ответа CRUD повтор блокируется: результат сверяется со списком
  по ID/полям, а для создания исключаются ID, существовавшие до отправки.
- `adminImageApi` читает подтверждения через authClient, без публичного fallback.
  Upload использует существующий image API, новые ID входят в PUT. Удаление из
  формы исключает ID; физическое удаление прежних файлов не выполняется.

Документ описывает текущую frontend-реализацию. Ограничения административного API,
непроверенные серверные сценарии и целевые production-изменения объединены в
[backend-plan.md](./backend-plan.md).

## Административное рассмотрение обращений (этап 7)

`adminOrderCasesApi` использует authClient: GET `/admin/actions/order-cases`
с state=OPEN/RESOLVED, limit=50, offset=page×50; GET `/{caseId}`;
PUT `/{caseId}/telegram-url?url=...`; POST `/{caseId}/resolve?outcome=...&comment=...`.
Тела JSON и параметра version нет. Детали принимаются только с совпавшим caseId.
Обе схемы и параметры повторно прочитаны из работающей OpenAPI 16.10.2026.
Без total следующая страница доступна при 50 элементах; из пустой страницы
можно вернуться назад. Невалидные state/page нормализуются, небезопасный offset
не отправляется. Выбранное обращение хранится в UI query case.

Query keys: `["admin", session, "order-cases", "list", state, page]` и
`["admin", session, "order-cases", "detail", caseId]`. Чтение запускается после
успешной проверки ADMIN существующим AdminAccess; queryFn также проверяет текущий
access snapshot. Перед записью заново читаются профиль и детали, без доверия
staleTime; повторно проверяются доступ, caseId, kind, исходный статус и матрица
решений. Старый GET деталей отменяется. Валюта сумм берётся только из обращения;
отсутствующая валюта и техническое CREATE явно обозначаются, суммы не умножаются.

`getAdminOrderCaseOutcomes` разрешает только OPEN: cancellation — CANCELLED/REJECTED,
dispute — BUYER и SELLER лишь из ON_THE_WAY, payment appeal — BUYER/SELLER.
RESOLVED, LEGACY и неизвестный вид не разрешают новое решение. Комментарий
непустой. Telegram использует существующий URL parser: HTTPS, точные t.me/telegram.me,
без credentials/порта и с путём. Действия возврата денег отсутствуют.

Формы, исходный контекст и единый busy/attempt сохраняются в памяти QueryClient
под `["admin", session, "case-operation", caseId]`, переживая закрытие/remount
и refresh токена. Logout/expiry/смена аккаунта очищает namespace через существующий
PrivateDataBoundary; поздние ответы не восстанавливают старый scope. Dirty-ввод
защищён общим unsaved-changes guard, pending блокирует закрытие и навигацию.
После unmount до записи цепочка останавливается; начатая запись сохраняет результат
в том же scope. Offline-очередь и автоматический retry отключены.
Guard общий для экземпляров одного QueryClient; между вкладками и после reload
он не сохраняется. Конкурирующие решения разных администраторов проверяет сервер.
Нетронутая Telegram-ссылка обновляется из свежих деталей без потери комментария.
Dirty-ссылка сохраняется; если preflight обнаружил другой серверный baseline,
PUT не отправляется до явного повторного сохранения после просмотра свежих данных.
Совпавшая с серверной ссылка повторного PUT не создаёт.

POST и PUT взаимно исключаются. Неопределённый исход блокирует обе операции:
проверяется только GET деталей. Решение подтверждается state=RESOLVED плюс точными
outcome/resolutionComment, ссылка — сохранённым URL. OPEN не доказывает отказ;
изменение orderStatus не используется как подтверждение. Принятый запрос остаётся
принятым при failed GET. Другое серверное решение показывается с сохранением ввода.
N1-коды ALREADY_RESOLVED, INVALID_TRANSITION и INVALID_OUTCOME различаются;
любой 400/409 не подменяется одним из них. ALREADY_RESOLVED запрещает повтор даже
при запаздывающем OPEN. После другого явного отказа повтор возможен только явно,
после успешного контрольного чтения и синхронизации. Подтверждённая Telegram-запись
разблокирует дальнейшее рассмотрение явной кнопкой; решение не отправляется снова.

После записи перечитываются детали и все кэшированные страницы обеих очередей.
Решение также отменяет старые GET и обновляет административные списки заказов,
customer/seller lists и историю этого заказа текущего private scope, если такие
queries существуют. Каталог, другой аккаунт и истории других заказов не затрагиваются.
При failed GET деталей остальные связанные списки всё равно обновляются;
ошибка синхронизации оставляет повтор чтения, сохраняя принятый/неопределённый исход.
UI не устанавливает статус заказа локально. Backend-права и реальные переходы
не подтверждены mock-тестами и требуют отдельной серверной приёмки.

## HTTP

Основные файлы:

- `src/shared/api/axios/instances.ts` — Axios clients и interceptors;
- `src/shared/api/axios/authSessionAdapter.ts` — интерфейс связи HTTP-инфраструктуры с session;
- `src/shared/config/env.ts` — выбор API URL;
- `app/api/config/route.ts` — runtime URL для браузера;
- `src/shared/lib/errorHandler.ts` — нормализация ошибок.

Используются два клиента:

- **`publicClient`** — публичные запросы и auth endpoints.
- **`authClient`** — защищённые запросы, bearer token и refresh при `401`.

Новый HTTP client без отдельного архитектурного решения не создаётся. Доменные API находятся в `src/entities/<entity>/api` и используют готовые clients.

Auth API, store, `useAuth`, инициализация и refresh lifecycle принадлежат
`entities/session`. Axios не импортирует эту entity: `AuthProvider` в app layer
регистрирует `AuthSessionAdapter` с операциями refresh и обработки истёкшей
сессии. `features/auth` содержит только сценарный UI, guards и auth-действия.

## Base URL

Сервер выбирает URL в порядке:

1. `API_BASE_URL`;
2. `CLIENT_API_BASE_URL`;
3. `NEXT_PUBLIC_API_URL`;
4. local fallback только вне production.

Браузер получает `CLIENT_API_BASE_URL` через `GET /api/config`. Local URL в production разрешается только при `ALLOW_LOCAL_API_URL=true`.

Загрузка runtime config общая для public/auth clients и `preloadApiConfig`.
Deadline 10 секунд охватывает fetch и чтение JSON; при истечении transport
отменяется, а ошибка нормализуется в `ApiError` (`TIMEOUT`, 408). Ошибки HTTP,
JSON и формата `apiUrl` также нормализуются. После отказа pending promise
сбрасывается, следующая попытка может загрузить config заново; поздний ответ
не заменяет актуальный кэш. Вне production сохраняется прежний fallback на
`getServerApiBaseUrl`; успешно полученный fallback кэшируется.

`apiUrl` проверяется и нормализуется по общим правилам `shared/config/env`;
ограничения окружения проверяет серверный route. AbortSignal отдельного
запроса или смена поколения сессии отменяет только его ожидание config.
Interceptor назначает Axios `baseURL`, сохраняя endpoint в `url`, поэтому
повтор после 401 не удваивает root-relative префикс. Абсолютный endpoint
остаётся абсолютным; query params передаются обычным механизмом Axios.

Текущая валидация принимает `http:` и `https:`. Требование HTTPS для публичного browser API пока зафиксировано только в `.env.example`, но не обеспечено кодом. Root-relative URL допустим для browser same-origin proxy, однако server-side `API_BASE_URL` должен быть абсолютным.

## Текущий auth flow

- `AuthProvider` регистрирует session adapter и запускает инициализацию auth;
- `access_token`, `refresh_token` и `token_created_at` хранятся через `js-cookie`;
- `authClient` добавляет `Authorization: Bearer <access_token>`;
- при `401` interceptor вызывает refresh через adapter, а параллельные запросы ожидают один refresh;
- `POST /auth/refresh` получает refresh token в `X-Refresh-Token`;
- после успешного refresh исходный запрос повторяется;
- при ошибке токены очищаются и пользователь направляется на `/auth/login`;
- logout сейчас очищает токены только на клиенте;
- `middleware.ts` предварительно защищает `/dashboard` и `/admin` по наличию cookies; проверка роли админки дополнительно выполняется через backend-профиль.

`authStore.refreshToken()` объединяет timer, initialization и конкурентные 401
в один pending promise текущего поколения. Auth API возвращает access token;
его запись, auth state и перезапуск таймера принадлежат store и выполняются
только для актуального поколения. Logout и начало нового login отменяют
старое поколение; поздний success/error не меняет новую сессию. Успешный
refresh того же аккаунта сохраняет accountRevision.

Adapter передаёт HTTP-слою `getSessionSignal()`: неперсистентный AbortSignal
поколения. Исходный запрос и replay сохраняют этот сигнал. И первый запрос,
и очередь ждут refresh не более 10 секунд; timeout, AbortSignal запроса или
смена поколения удаляют subscriber, listeners и таймер ожидания. Перед replay
и после асинхронной подготовки URL актуальность проверяется повторно.
Отмена одного ожидания не отменяет общий refresh для остальных запросов.
Token manager отдельно инвалидирует выполняющиеся callbacks при stop/start/reset,
чтобы старый callback не планировал retry и не завершал новую сессию.

`auth-storage` сохраняет только поле `user`, без токенов и пароля. Сессия
использует безопасный storage adapter: при отказе доступа, get/set/remove он
переходит на память до конца жизни экземпляра. Это исключает повторное чтение
устаревшего значения после неудачной записи/удаления. Persistence не отменяет
login/refresh/logout; initialize завершается с `isInitialized` для актуального
поколения. Cookies остаются источником наличия токенов, память не заменяет их.

Специальные ошибки login/resend читаются как unknown. Ветка подтверждения
требует `WAITING_VERIFY` + `VERIFY_EMAIL`; cooldown требует
`VERIFICATION_COOLDOWN` и конечное неотрицательное число `retryAfterSec`.
Остальные отказы преобразуются в `ApiError` с сохранением исходной ошибки.
`VerificationCodeResponse` различает успех с `userId` и cooldown с
`retryAfterSec`; ноль разрешает немедленный повтор, дробные секунды в диалоге
округляются вверх для обратного отсчёта.

Это действующая реализация, но не целевая production-модель: токены доступны JavaScript. Риски, требования к backend и критерии миграции описаны в [backend-plan.md](./backend-plan.md).

Login/register сохраняют `redirect` при переключении форм, после входа и
подтверждения почты на всех размерах экрана. Public API `entities/session`
экспортирует `getPostAuthRedirectPath` и `getAuthSwitchPath`: общий sanitizer
принимает локальный путь с query/hash, проверяет origin и нормализованный путь,
отклоняет внешние адреса, обратные слеши, управляющие символы и переходы на auth.
Некорректный адрес заменяется `/`. Auth routes используют `Suspense` для чтения
query-параметров через `useSearchParams`.

Гостевые `add-to-cart` и `toggle-favorite` передают в `AuthRequiredDialog`
callback входа: текущие pathname/query берутся при нажатии «Войти» и проходят
`getAuthSwitchPath`. После login либо register/verify пользователь возвращается
на исходную страницу; добавление товара автоматически не повторяется.

Дополнительные открытые ограничения:

- server guards определяют auth только по наличию cookie и не подтверждают backend session.

## Поиск товаров и сессия

`userApi.getUser/getProfileUser` и соответствующие queries возвращают core
`UserBaseModel/UserProfileModel` с `imageId`, без `image`. Ошибка metadata не
влияет на профиль, sellerId или доступность действий; ошибка core по-прежнему
блокирует проверку владельца. Существующие scoped `userKeys` сохранены.

`orderApi.getSellerOrders/getCustomerOrders` кэшируют `ListOrdersDto[]` без
enrichment, под прежними scoped `orderQueryKeys`. `OrdersWidget` отдельно
загружает metadata и собирает `ListOrdersModel` для отображения и диалогов.
`productApi.getUserProducts` возвращает `ProductDto[]`; шапка и список используют
один scoped infinite key: `productKeys.userLists(), 100, undefined, DATE_DESC`.
Шапка считает продления по первой сотне, как прежде; список показывает по 12
карточек из общего кэша, затем читает следующую сотню существующим cursor API.
Отдельный renewal-check query больше не используется. Delete/extend/update
инвалидируют общий core cache через существующую user-ветку.

Metadata загружается только отображающими картинки widgets через
`useImageMetadataQuery`: ключ `imageMetadata, ...ids` содержит отсортированные
уникальные положительные IDs, запрос получает AbortSignal. Профиль и редактор
аватара используют тот же image cache; списки запрашивают batch. Public API
`mapImageMetadata` синхронно сопоставляет DTO с metadata по ID, без сети и
изменения core cache. `ImageMetadataFeedback` показывает локальную загрузку
или ошибку с retry только metadata; fallback не блокирует данные и формы.
Публичные catalog/detail чтения и сопоставление изображений редактора товара
сохраняют прежний контракт.

`POST /products/find` не получает `includeAdult`: возрастной доступ определяет
backend по пользовательскому bearer token. Браузерный поиск авторизованного
пользователя идёт через `authClient`; гостевой поиск, SSR и sitemap — через
`publicClient`. Недействительный токен может дать успешную выдачу без 18+;
пустой результат не преобразуется фронтендом в ошибку доступа. Локальный
age gate категории остаётся предупреждением, а не подтверждением возраста серверу.

`useAuth` отдаёт неперсистентный `sessionKey`: `null` для гостя, номер ревизии
для инициализированной сессии. Композиция передаёт его в `useProductsInfinite`
и ожидает инициализацию auth перед запросом. Ключи каталога разделены по
сессиям; вход, выход и успешное обновление токена переключают выдачу. Токены
и персональные данные в query keys не помещаются. SSR initial data используются
только в гостевом кэше, поэтому не подавляют авторизованную загрузку.

Infinite catalog сохраняет страницы при ошибке хвоста или фонового refetch.
`useInfiniteProducts` отдаёт `hasNextPageError` и `isLoadMoreBlocked`:
автозагрузка ждёт окончания любого чтения и после отказа хвоста остаётся
на паузе, даже если reconnect успешно обновил страницы. Ручной retry хвоста
вызывает `fetchNextPage`; смена query key сбрасывает паузу. Initial/background
retry вызывает `refetch`, не заменяя загруженные карточки общим error screen.

`UserProductsList` использует те же состояния для ручной пагинации: после
ошибки хвоста сохраняет карточки и предлагает `fetchNextPage`, а initial и
background error повторяются через `refetch`. Локальный показ по 12 товаров
не запрашивает уже загруженные страницы повторно.

Публичные товарные DTO поддерживают `EXTERNAL_PRODUCT`, `count: number | null`
и `externalUrl: string | null`. `count=null` означает неограниченный остаток;
публичный backend скрывает внешнюю ссылку значением `null`, покупатель её не видит.
Внешний товар участвует в обычных операциях корзины и создании заказа.
Это не даёт обычному продавцу права редактировать товар бота.
Количество внутри snapshot товара в заказе остаётся числом заказанных единиц.

## Суммы и этапы заказа

В `ListOrdersModel` / `ListOrdersDto` поле `prepaymentAmount` хранит готовую
предоплату за всё заказанное количество, `totalPrice` — готовый остаток к оплате.
`getOrderPaymentBreakdown` читает эти суммы без умножения на количество и без
пересчёта из `product.price` / `product.prepaymentAmount`. Полная стоимость товаров
для отображения — сумма этих двух компонентов; доставка показывается отдельно.
Признак `hasPrepayment` определяется как `order.prepaymentAmount > 0`, включая
`EXTERNAL_PRODUCT`; он управляет финансовой разбивкой, этапами и подсказками.

Первичное подтверждение обычного продавца по-прежнему вызывает
`POST /order/{id}/AWAITING_PREPAYMENT`. Несмотря на название endpoint, frontend
не устанавливает статус локально: после действия перечитывает заказ. Backend
возвращает `AWAITING_PREPAYMENT` при наличии предоплаты и `AWAITING_PAYMENT`
без неё. Действия покупателя доступны по фактическому `actualStatus`.

До создания заказа корзина располагает только ценой и предоплатой за единицу
товара. Её разбивка помечена как предварительный расчёт, включая внешние товары;
после создания во всех диалогах используются суммы из ответа заказа.

## Ошибки и типы

- Axios errors преобразуются в `ApiError`, кроме запросов с `_skipErrorTransform`;
- UI не должен зависеть от сырого `AxiosError` после interceptor;
- ошибки нельзя превращать в пустой результат без осознанного UX и логирования;
- password, token, authorization headers, cookies, request body и чувствительные query params нельзя писать в browser/server logs и error tracking;
- request/response и query params должны быть типизированы;
- DTO mapping хранится рядом с доменом;
- неподтверждённые поля и статусы не добавляются.

При чтении собственных настроек доменные ответы `404 + ACCOUNT_NOT_FOUND`
для `GET /accounts`, `404 + SOCIAL_NETWORK_NOT_FOUND` для
`GET /social-networks` и `404 + TRANSFER_NOT_FOUND` для `GET /transfer`
означают отсутствие записей и преобразуются в `[]` внутри соответствующего
API-модуля. Формы позволяют добавить первую запись. Другие `404`, ошибки
авторизации, сервера и сети остаются ошибками с возможностью повторной загрузки.
Это правило не применяется к чтению реквизитов другого участника
через `GET /accounts/participant/{id}` и к операциям записи.

Доменные DTO находятся в `model` соответствующих entities.

В seller edit количество имеет явное представление: `0` означает отсутствие
остатка, пустое поле — `null` (без ограничения). Несвязанные правки сохраняют
эти значения; создание по-прежнему требует положительный остаток. Счётчики
проверяются как safe integer, деньги — на конечность после parsing и перед
записью. Дробные суммы сохраняются без округления до целого.
Admin read DTO допускает `prepaymentAmount: null`; mapper явно преобразует его
в числовой 0 формы и PUT, с подписью «Без предоплаты». Write DTO остаётся числовым.
Seller submit требует валидный ID и инициализированный товар с тем же ID.

Только 404 основного `GET /product/{id}` классифицируется как
`ProductNotFoundError`. Ошибка image metadata, включая 404, сохраняет общий
error/retry и не означает отсутствия товара. Пустой успешный metadata-ответ
допускается. Неверный route ID блокируется до запроса, включая ручной refetch.

Retry деталей привязан к источнику ошибки: client query повторяется через
`useProductDetails.refetch`, initial SSR error — через `router.refresh`.
Восстановленный после SSR ошибки snapshot записывается в существующий detail
cache до включения клиентского чтения: изменение `initialData` само по себе
не обновляет созданный query. `isFetching` и pending route refresh блокируют
повторное нажатие; подтверждённое отсутствие и invalid ID не предлагают retry.

`entities/image` владеет `ImageMetadata`, `ImageResponse`, `ImageTag`, image API,
query hooks и `attachImages`. В `src/shared/model` остаётся только нейтральный
тип `Currency`.

Диагностика ошибок проходит через `serializeApiError` в `shared/lib/errorHandler`:
в консоль передаются только HTTP status, известный code (неизвестный заменяется
на `UNKNOWN`), нейтральное сообщение и pathname без query, hash, origin и URL credentials.
Backend message, details, timestamp, stack, config, request и исходный error
в логи не передаются. `ApiError` для обработки в UI сохраняет прежние поля;
его нельзя передавать в console/error tracking напрямую. HTTP и timer logger
по-прежнему работают только в development; остальные error calls используют
тот же serializer и в production. Это правило действует и для будущего error tracking.

## Server и client state

TanStack Query хранит backend data, loading/error state, cache и invalidation. Query keys находятся рядом с сущностью.

Zustand используется для session state в `entities/session` и другого локального client state. Исключение — `cartQuantityStore`: он хранит optimistic projection количества, revisions и последнее подтверждённое значение, синхронизируясь с cart query. Это не второй источник истины о корзине; подтверждённые данные и остатки по-прежнему приходят с backend.

`PrivateDataBoundary` в app layer подписан на auth store: login/logout, смена аккаунта и автоматическое завершение отменяют и удаляют приватные/admin queries, очищают проекцию корзины и черновик товара. Клиентское поддерево перемонтируется при смене владельца, сбрасывая формы и selection. Успешный refresh того же аккаунта сохраняет scope и ввод. Завершение не зависит от кнопки выхода или успешной записи storage.

Обычные приватные ключи имеют вид `["private", accountRevision, ...entityKey]`. Scope передаётся через нейтральный React context из `shared/lib/query`; соседние entities не импортируют session. Это относится к профилю, корзине, избранному, заказам, адресам, реквизитам, доставке, контактам и собственным товарам. Публичные ключи сохраняют прежний формат. Приватные чтения, включая вложенную image metadata, получают AbortSignal; scoped key изолирует результат даже без поддержки отмены транспортом.

`usePrivateMutation` проверяет владельца перед отправкой и settlement callbacks. Ручные cache writes используют захваченный scope; корзина дополнительно проверяет его после каждого ожидания перед записью общей проекции. Очередь подтверждающих чтений разделена по scope. Количества больше не восстанавливаются из localStorage: после reload источником служит GET корзины.

Контрольное чтение корзины записывает snapshot только в scoped query cache;
единственный владелец проекции в `PrivateDataBoundary` синхронно применяет его
перед validation текущей revision. Consumers карточек не повторяют синхронизацию.
Очередь и обязательное чтение после каждой записи количества сохранены.

Toggle избранного откатывает только свою позицию, если её revision не заменена
новой операцией. Добавление берёт типизированные pages каталога; итоговая
invalidation списка выполняется при обнулении общего для scope счётчика операций:
регистрация до первого await в onMutate, снятие синхронно в onSettled, включая отказ.
Это обеспечивает одну сверку при одновременном settlement независимо от момента,
когда TanStack снимает pending. Новый toggle отменяет текущий GET и запускает
сверку после своего settlement. `useAddToFavorites` / `useRemoveFromFavorites` принимают `onError`
с нормализованным `ApiError`; feature показывает одно уведомление об отказе.
`useRemoveFromCart` / `useCartItemRemoval` передают `onError(error, productId)`
на уровень feature/widget. Успешное контрольное чтение корзины не скрывает
ошибку DELETE; pending удаления очищается по завершении каждой операции.
Cancellation и callbacks завершённого scope не показывают уведомлений.

Черновик товара содержит `owner` — ID подтверждённого `/participant`. Восстановление ждёт профиль текущего scope; legacy и чужой owner не принимаются, включая reload. При logout/смене аккаунта очищаются память и storage, а принадлежащие memory draft blob URL освобождаются без DELETE серверных изображений. Отказ storage не позволяет восстановить чужой черновик; refresh того же аккаунта его не очищает.

Изображения редактора сохраняют исходные `imageIds` независимо от полноты metadata;
preview сопоставляется только по `metadata.id`. Для отсутствующего preview показана
заглушка с ID; исключение из набора и последующий cleanup требуют явного удаления.
Во время восстановления фото черновика и после его ошибки добавление/удаление фото
блокируется до retry либо явной очистки формы. Очистка отменяет применение позднего
restore; ошибка восстановления не снимается новым upload.

`imageApi.saveImage` отклоняет пустой ответ и массив с невалидными ID (не положительные
безопасные целые числа). Product/payment используют существующее состояние ошибки
и повторный выбор файла; невалидный ID не становится успешным upload.
`useMultipleImageUpload` освобождает blob URL при unmount, кроме URL, владение которыми
подтверждает переданный callback. Для create это только preview текущего memory draft;
edit не передаёт владение. Освобождение URL не выполняет серверный DELETE.

`useUpdateProduct` и `useUpdateUser` подтверждают только PUT и обновляют кэш;
удаление изображений не входит в entity mutation. Редакторы отдельно вызывают
`useImageCleanup` из `features/image-upload` для ID, исключённых подтверждённой
записью. При отказе DELETE показывается «сохранено, очистка не завершена»;
повтор выполняет только незавершённые DELETE по одному ID, без PUT и без
повторения успешных удалений. Подтверждённые данные не откатываются. До завершения
очистки сохранённый редактор блокирует новую запись; cleanup прекращается при
unmount или смене приватного scope. При отказе PUT очистка не начинается.

`useImageUpload` хранит preview и ID успешно загруженного аватара вместе.
`imageState` различает unchanged/uploading/uploaded/failed/explicitlyRemoved;
при uploading/failed сохраняется предыдущий выбор. Ошибка файла или upload
не означает удаления. `resetImageState` возвращает unchanged, `removeImage`
фиксирует явное удаление; оба отменяют применение прежнего upload по ревизии.
Поздний ответ после нового выбора, unmount или смены scope игнорируется.
Blob URL создаётся только после успешного upload и освобождается при замене,
сбросе, удалении или unmount, без серверного DELETE.

Форма профиля проверяет актуальное состояние через `getImageState` перед PUT:
незавершённая загрузка блокирует также programmatic submit, а во время записи
изменение аватара заблокировано. При отказе замены показывается прежнее фото
и сохраняется его выбор. Cleanup исходного аватара выполняется только после
подтверждённого PUT с явным удалением; payload и backend-контракт не изменены.

Widget формы товара ожидает `mutateAsync` и cleanup, повторно проверяет readiness,
завершение upload и соответствие загруженного edit target перед записью. Он отправляет
отдельный snapshot значений и imageIds, исключает повтор после подтверждения записи
и обновляет dirty baseline edit. Create очищает только отправленную ревизию локального
черновика; autosave прекращается после успеха. Поздний success завершённого экземпляра
не сбрасывает форму/черновик и не запускает переход; его таймер навигации отменяется
при unmount. Это защита клиентского lifecycle, без изменения backend-контрактов.

Подтверждённые delete/extend товара инвалидируют публичную ветку
`productKeys.lists()` вместе с detail и scoped собственными товарами.
Это включает каталоги всех session keys; TTL запросов не меняется.

## Адрес доставки в checkout

Новый адрес можно добавить в checkout через существующую `AddressForm` и
`POST /address`: он сохраняется в аккаунте, а заказ по-прежнему получает
`addressId`. Пока форма открыта, адрес сохраняется или ожидается обновление
списка, отправка заказа заблокирована. Отмена до сохранения оставляет прежний
выбор адреса и остальные данные checkout.

Клиент `addressApi.create` не возвращает созданный адрес. После успешного
сохранения checkout перечитывает `GET /address` и автоматически выбирает
только единственный новый `ACTIVE` адрес, совпавший по всем полям ввода.
Порядок списка и максимальный ID не используются. При неоднозначности
прежний выбор сбрасывается и требуется ручной выбор.

Ошибка создания оставляет форму и введённые данные. Если создание подтверждено,
но перечитывание списка не удалось, действие «Повторить загрузку» выполняет
только чтение, без повторного `POST`. Список остаётся в TanStack Query; checkout
хранит выбранный ID и состояние локального сценария, а не копию адреса.

## Товары и доставка в checkout

Выбор всех товаров инициализируется при первой непустой загрузке checkout.
Refetch, изменение количества и удаление последней выбранной позиции сохраняют
явный пустой выбор; новые позиции не добавляются в него автоматически.
Смена владельца перемонтирует checkout и начинает новый выбор.

Создание заказа различает успех, подтверждённый отказ и неизвестный результат.
Подтверждёнными считаются только ответы 4xx с известными доменными кодами
`COUNT_INVALID`, `OWN_PRODUCT_PURCHASE_FORBIDDEN`, `PRODUCT_NOT_PURCHASABLE`,
`TRANSFER_NOT_FOUND`, `ACCOUNT_NOT_FOUND`. Остальные ошибки, включая потерю
ответа и 5xx, не доказывают отсутствие записи. При неизвестном результате
повтор оформления блокируется; UI предлагает перечитать корзину и открыть покупки.
Отсутствие совпадения в списке не снимает неопределённость.

Флаги выполняющейся и неопределённой попытки принадлежат `features/order-create`
и хранятся в памяти по AbortSignal приватного scope. Они переживают закрытие
диалога и клиентские переходы между страницами, сохраняются при refresh токена
и изолируются при смене сессии. Payload, адрес и комментарий в этом состоянии
не сохраняются; оно не является серверной гарантией идемпотентности и не переживает
полную перезагрузку документа.

Retry подтверждённых отказов сверяет актуальные selection, количество (включая
подтверждённую корзину), адрес, доставку, комментарий и readiness с исходной
попыткой. Изменение требует возврата к проверке оформления. Успешные позиции
и `PRODUCT_NOT_PURCHASABLE` повторно через Retry не отправляются.

Товары объединены по продавцам. Выбор доставки хранится независимо для каждого
продавца: единственный активный способ выбирается автоматически, несколько
способов открываются из компактной строки в диалоге (на мобильных — нижняя
панель). Изменение применяется кнопкой; отмена сохраняет прежний выбор.
Загрузка, ошибка с повтором и отсутствие способов отображаются внутри группы.

Доставка учитывается один раз на выбранного продавца, а не на каждую позицию.
Снятие выбора со всех его товаров исключает доставку из итога, сохраняя ещё
доступный способ для повторного выбора. Пока способ не определён хотя бы у
одного выбранного продавца, общая доставка помечается как нерассчитанная.
Существующие блокировки оформления и `transferId` в payload не изменены.

При недостаточном остатке карточка предлагает явно уменьшить количество до
доступного через существующий механизм синхронизации корзины. Нулевой остаток
позволяет исключить товар из заказа без удаления из корзины; автоматического
уменьшения количества нет.

## Чувствительные операции

- `PUT /participant/password` сейчас отправляет `oldPassword` и `newPassword` в query string. Для production нужен подтверждённый body-контракт и redaction на proxy/backend.
- `POST /auth/password/reset` отправляет email в query, а UI может показывать backend message. Backend должен исключать account enumeration и определить rate limit, single-use, expiry и session revocation.
- Комментарии к заказу и delivery URL в части order endpoints также передаются через query. Чувствительные пользовательские значения должны переноситься в body после согласования контракта.
- Изображения `ORDER` читаются и загружаются через authClient; перед production требуется проверить серверный object-level доступ по участнику заказа на реальных изолированных данных.
- Платёжные реквизиты продавца запрашиваются по `participantId`; backend должен подтверждать object-level доступ в контексте заказа.
